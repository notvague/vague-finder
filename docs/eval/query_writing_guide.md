# 평가 질의 작성 규칙 — 3차 세트부터 (v10~)

작성: 황찬혁 · 대상: 최정현 · 이연우 · 제출 기한: 세트마다 정한다

> **경위.** 2차 세트 v09(100건, 2026-10-09)는 이 문서의 계획과 달리 **Claude 초안 + 황찬혁 검토**로 만들었다 — 곡 메타데이터·표지만 보게 하고 태그·요약·가사는 못 보게 했으며, 황찬혁이 전수 검토해 10곡을 교체했다(`src/eval/schema.py`의 `v09` 주석). v09의 봉인 test 38건은 2026-10-09에 한 번 열렸다. **다음 홀드아웃(3차 세트)은 아래 규칙대로 팀원이 직접 쓴다.**

## 왜 쓰나

지금 평가 세트는 dev 57 · test 25건이다. test는 질의 한 건이 Hit@10 4%p라서, 어떤 개선안도 "우연보다 낫다"고 말할 수 없다.
게다가 test 25건은 이미 여러 번 선택에 쓰여 홀드아웃 역할을 잃었다. **새 질의 100건**을 더해 dev 62 · 봉인 test 38로 나눈다(전체 test 비율 25~35% 규칙).
봉인 test는 최종 설정 하나로 마지막에 한 번만 연다.

튜닝을 한 사람(찬혁)이 쓰면 결과가 유리하게 치우치므로 두 분이 쓴다. 3차 세트는 **50건씩**을 기준으로 하되 세트마다 정한다.

## 가장 중요한 규칙 셋

1. **기억으로 먼저 쓰고, 정답은 나중에 확인한다.** 곡의 `meta.json`·태그·가사 요약을 열어 보고 그 표현을 옮겨 쓰지 않는다.
   9월에 그렇게 쓴 초안 26건은 전부 Top-10에 들어와 폐기했다(정답의 `sound_tags` 토큰을 그대로 썼다).
2. **제출 전에 시스템에 넣어 보지 않는다.** 검색이 찾는 쪽으로 표현을 고치게 된다. 그러면 봉인 test가 눈가림이 아니다.
3. **제목·가수 이름을 쓰지 않는다.** "제목이 영어 한 글자" 같은 **형태** 기억은 된다. 가사 조각은 된다(정확하지 않아도 된다).

## 어떤 질의를 쓰나

실제 상황을 떠올린다: 노래가 머릿속에 있는데 제목도 가수도 모른다. 친구에게 뭐라고 설명하겠는가. 한두 문장, 말하듯이.

기존 예(`docs/eval/queries.json`):

- "2000년대 후반에 싸이월드 배경음악으로 엄청 유행했던 곡인데, 여자애들 여러 명이 부르는 빠른 댄스곡이었어. 제목이 알파벳 세 글자였던 것 같은데"
- "도깨비 드라마에 나온 노래인데 피아노 반주에 남자 보컬이 감성적으로 불렀어"
- "도입부 멜로디에 휘파람 소리가 기억나. 남녀 듀엣 곡인데 남자는 랩을 하고 여자가 노래를 불렀던 것 같아"

**한 질의는 곡 하나를 가리켜야 한다.** 설명이 코퍼스의 곡 수십 곡에 맞으면("빨간 표지 노래", "슬픈 발라드") 그것은 범주형 질의다.
범주형은 세트에 몇 개 있어도 되지만 의도한 것이어야 하고, 아래 CSV의 `target_scope`에 `categorical`로 적는다.

## 50건의 구성 (사람당)

| 유형 | 건수 | 쓰는 법 | CSV `modality_focus` / `tier` |
|---|---|---|---|
| 텍스트 단서 | 27 | 상황·시대·가수 유형·가사 조각·드라마/예능/애니 같은 외부 맥락·제목 형태 | `text` / `vague` |
| 소리 단서 | 10 | 악기 편성, 음색, 템포, 보컬 질감, 도입부 소리. **가사·제목 없이** 소리만으로 | `audio` / `vague` |
| 표지 단서 | 8 | 앨범 커버의 **실제** 모습(색·구도·인물·사물). 제출 전에 `cover.jpg`로 확인하고, 못 봤으면 `label_status`를 `pending_cover`로 | `image` / `vague` |
| 틀린 기억 | 5 | 위 유형 중 하나를 쓰되 **단서 하나를 일부러 틀리게** (성별·시대·솔로/그룹·장르 중 하나). 어느 단서가 틀렸는지 `notes`에 적는다. 나머지 단서로는 곡이 특정돼야 한다 | 해당 focus / `misinformation` |

- 외부 맥락(드라마·예능·애니·챌린지·광고) 질의를 텍스트 27건 중 **8건 이상** 넣는다. 지금 세트에서 가장 많이 놓치는 유형이고, 나무위키 Context 경로의 효과를 재는 데 필요하다
- 소리·표지 질의는 그 단서만으로 찾아야 하므로 텍스트 단서(가사·상황)를 섞지 않는다. 섞고 싶으면 `multimodal`로 표시한다(사람당 2건 이하)
- 저작권·초상권 때문에 가사를 길게 인용하지 않는다. 한 구절(10자 안팎)까지

## 정답 확인

정답 곡이 **코퍼스 3,010곡 안에 있어야 한다.** 멜론 곡 ID를 적는다. 로컬 `data/all_songs.jsonl`에서 확인한다.

```bash
# 제목·가수로 찾기 (대소문자 무시)
grep -i '"title": "[^"]*밤편지' data/all_songs.jsonl | python3 -c "import sys,json; [print(json.loads(l)['song_id'], json.loads(l)['metadata']['title'], json.loads(l)['metadata']['artist']) for l in sys.stdin]"
```

```bash
# ID가 코퍼스에 있는지
grep -c '"song_id": "30486509"' data/all_songs.jsonl
```

- 없으면 다른 곡으로 바꾼다. 코퍼스에 없는 곡은 어떤 설정으로도 못 찾아 점수만 깔린다
- 같은 곡이 기존 89건의 정답에 이미 있으면 피한다: `grep -c '"30486509"' docs/eval/queries.json`
- 리메이크·커버·라이브 버전이 여러 개면 **원곡**을 정답으로 하고, 다른 버전이 코퍼스에 있으면 `notes`에 ID를 적는다(허용 정답 검토 때 쓴다)
- 정답 확인은 **질의를 다 쓴 뒤에** 한다(규칙 1)

## 제출

`docs/eval/query_writing_template.csv`를 복사해 채운다. 파일 이름은 `queries_v10_<이름>.csv`(세트 번호는 그때 것), 팀 드라이브 `vague-finder/eval/`에 올린다.
레포에 커밋하지 않는다(봉인 test는 병합 전까지 작성자 외에는 보지 않는다).

| 열 | 값 |
|---|---|
| `tmp_id` | 작성자 이니셜 + 번호 (`jh01`, `yw01`). 정식 ID와 dev/test 배정은 PM이 한다 — **작성자는 split을 고르지 않는다** |
| `query` | 질의 원문 |
| `tier` | `vague` 또는 `misinformation` |
| `modality_focus` | `text` · `audio` · `image` · `multimodal` |
| `category` | `mood` · `artist` · `lyrics` · `scene` · `genre` · `mixed` (대부분 `mixed`) |
| `clue_type` | `external_context` · `sound_texture` · `title_structure` · `era_group` · `composition` · `lyric_fragment` · `audio_only` · `image_only` · `mixed_av` 중 가장 가까운 것 |
| `target_scope` | `specific`(기본) 또는 `categorical` |
| `label_status` | `labeled`(기본) 또는 `pending_cover` |
| `positive_id` | 멜론 곡 ID |
| `positive_title` / `positive_artist` | 확인용 |
| `wrong_clue` | misinformation만: 어느 단서를 어떻게 틀리게 썼나 |
| `notes` | 단서 요약, 다른 버전 ID, 헷갈릴 만한 곡 |

제출 뒤 PM이 하는 일: ID 부여(`query_set=v10` 등, `src/eval/schema.py`의 `QuerySet`에 추가), 층화 무작위로 dev 62 · test 38 배정, 분석 캐시 생성, 스키마 검증(`src/eval/schema.py`).
허용 정답 검토는 지금 하지 않는다 — 최종 설정의 top-10에 한해 나중에 팀이 함께 한다.
