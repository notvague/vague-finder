재질문에서 이미 제공한 성별·장르를 다시 묻지 않도록 하는 작업 계획

작성일: 2026-10-11. 이 문서는 구현 계획이며, 작성 시점에 서비스 코드는 수정하지 않았다.

1. 해결할 문제와 완료 후 동작

사용자가 첫 검색에서 명시한 정보를 새 정보처럼 다시 묻는 동작을 고친다.

| 최초 질의 또는 상황 | 기대 동작 |
| --- | --- |
| `중학생 때 나온 엄청 유명한 남자 아이돌 노래` | 성별 질문 제외. 필요한 출생 연도 질문은 유지. 이후 후보가 장르로 갈리고 한도가 남으면 장르 질문 가능. |
| `남자 인디 노래인데 뮤비에 의자가 하늘에 떠있는 장면이 있어` | 성별과 현재의 일반적인 장르 질문 모두 제외. 다른 질문 슬롯이 없으므로 거절 버튼은 다음 후보 검색으로 진행. |
| `여자 보컬의 발라드` | 성별·장르 질문 제외. |
| 성별·장르 단서가 없는 질의 | 기존 후보 분포·우선순위에 따라 질문. |
| `뮤비에 남자가 의자에 앉아 있어` | 화면 속 인물만으로 보컬 성별을 안다고 판단하지 않음. |

`인디`는 세부 음악 장르를 하나로 확정하는 값은 아니다. 다만 사용자가 이미 음악의 성격을 말했으므로, 이번 작업에서는 현재의 포괄적인 `어떤 장르에 가까웠나요?`를 반복하지 않는 정책을 적용한다. 향후 세부 장르를 묻고 싶다면 별도의 질문 설계로 다룬다.

2. 코드로 확인한 원인

- `src/retrieval/clarify.py:246`의 `stated_in_query()`는 이미 명시한 슬롯을 판별하지만 질문 제외에 쓰이지 않는다. 주석에는 과거 오기억 평가 9건 중 3건의 회수 효과 때문에 다시 묻도록 했다고 적혀 있다.
- 같은 파일의 `pick_question()`은 출생 연도 처리 이후 `pick_data_question()`으로 넘어간다. 후자는 후보 분포와 `asked_slots`만 확인한다. 원문에 준 정보는 `asked_slots`에 없으므로 다시 질문한다.
- `tests/test_clarify_question.py:115`는 이미 여성이라고 말했어도 성별을 다시 묻는 동작을 명시적으로 검증한다. 이번 수정은 이 과거 정책을 바꾸는 작업이다.
- `src/backend/schemas/search.py:162`의 `ClarifyRequest`와 `src/frontend/static/map.js`의 `requestClarification()`에는 원래 질의에서 이미 알려준 정보를 전달하는 계약이 없다. 서버에 있는 `stated_in_query()`만 고쳐도 화면의 지연 질문 경로는 해결되지 않는다.
- `src/retrieval/query_analyzer.py`의 `rule_fallback()`은 `vocal_gender=None`, `genre=""`인 분석을 반환한다. 두 사용자 예시에서도 동일했다. 분석 필드가 비어 있다는 이유로 원문의 명시적 단서를 잃으면 안 된다.

확인 범위: 외부 모델·실제 DB 없이 혼합 후보 10곡으로 재현했다. 분석에 `남성`과 `인디`를 직접 채워도 즉시 질문과 지연 질문 모두 성별을 선택했고, 성별을 물은 이력을 넣으면 장르를 선택했다. 관련 기존 테스트 2건도 통과했다. 실제 사용자 요청의 Gemini 분석 결과를 확인한 것은 아니다.

3. 적용할 정책

- **최초 질의에 명시된 정보는 일반 재질문 대상에서 제외한다.** 후보에 반대 성별이나 다른 장르가 많아도 이 정책을 뒤집지 않는다. 후보가 다양하다는 사실은 사용자 기억이 틀렸다는 증거가 아니다.
- 아직 모르는 항목만 기존 우선순위로 확인한다. 후보를 가르지 못하거나 한도를 소진했으면 질문을 만들지 않는다.
- 물을 항목이 없으면 `clarify=null`로 처리하고, 화면에서 거절만 하는 기존 검색 흐름을 이용한다.
- `남자였는지 모르겠어`, `남자일 수도 있어`, `발라드인지 록인지 모르겠어` 같은 불확실한 표현은 확정 정보로 취급하지 않는다. `여자는 아니야` 같은 부정만으로 남성을 확정하지 않는다.
- 사용자가 요청하지 않은 자동 재확인 단계, 새 질문 슬롯, 세부 장르 질문은 이번 범위에 넣지 않는다. 오기억을 고치는 별도 기능은 후속 설계로 분리한다.

4. 상태와 API 계약

`known_slots`라는 재질문 전용 상태를 추가하는 방식을 권장한다. 이름은 구현 과정에서 조정할 수 있지만 다음 의미는 유지한다.

| 상태 | 의미 | 질문·턴 한도에 포함 |
| --- | --- | --- |
| `known_slots` | 최초 질의에서 이미 명시한 데이터 항목. `vocal_gender`, `genre`만 허용. | 아니오 |
| `asked_slots` | 현재 대화에서 실제로 답하거나 건너뛴 질문 이력. 기존 출생 연도 닫기 동작 포함. | 기존 규칙 유지 |
| `answers` | 실제 재질문 응답 누적. 후보 보정에 사용. | 기존 규칙 유지 |

원문에서 찾은 정보를 `asked_slots`에 끼워 넣거나 가짜 `answers`로 만들지 않는다. 그러면 질문 한도와 순위 보정에 불필요한 변화가 생긴다.

흐름:

1. `/search`가 원본 분석·원문에서 `known_slots`를 산출한다. 기존 분석에 출생 연도나 답변을 합쳐 검색값을 바꾸는 과정과 분리한다.
2. `SearchResponse`에 `known_slots`를 내려준다. 검색 요청에 같은 상태를 추가할 필요는 없다. 서버는 원문을 가진 분석에서 매번 동일하게 계산할 수 있다.
3. 화면의 `applyResponse()`가 `convo.knownSlots`를 응답 값으로 **교체**한다. 이전 검색 값과 합치지 않는다.
4. `requestClarification()`이 후보 ID·기존 상태와 함께 `known_slots`를 `/search/clarify`로 보낸다.
5. 질문 조회는 원문 재분석이나 추가 모델 호출 없이 해당 슬롯을 제외한다. 원문·전체 분석·출생 연도를 질문 조회 API에 다시 넣을 필요는 없다.

스키마는 `Literal["vocal_gender", "genre"]` 기반 목록, 기본 빈 목록, 최대 두 항목으로 제한한다. 중복 처리도 정규화 또는 422 중 하나로 명시하고 테스트한다. `ClarifyRequest`의 `extra="forbid"`는 유지한다. 필드를 생략하는 구버전 호출은 빈 목록으로 호환되지만 중복 방지 효과가 없으므로, 실제 화면과 리허설 호출부는 모두 갱신한다. 프론트 정적 파일 버전도 올린다.

이 값은 기존 분석 왕복처럼 질문 선택을 위한 클라이언트 상태다. 이를 신뢰 경계나 검색 필터로 확장하지 않는다.

5. 구현 순서

① 재질문 전용 명시 단서 판정

- `clarify.py` 또는 작은 별도 모듈에 부작용 없는 공통 함수(예: `known_slots_from_query(analysis)`)를 둔다.
- 원문을 증거로 사용한다. 분석에 성별·장르가 채워진 사실만으로 확정하지 않으며, 반대로 분석이 비어 있어도 명시적 원문 표현은 처리한다. 사용자 예시 두 개는 반드시 후자 조건에서도 통과해야 한다.
- 성별은 곡의 가창자·목소리를 수식하는 `남자 아이돌`, `여자 보컬`, `남자 인디 노래`, `남자가 부르는`, `남녀 듀엣` 등의 문맥을 다룬다.
- 장르는 `인디`, `인디록`, `인디 팝`, `발라드`, `힙합/랩`, `록/락`, `R&B/알앤비` 등 실제 지원할 표현을 명시하고 테스트한다. 무제한 사전 확장보다 현재 재질문 옵션 및 사용자 예시를 우선한다.
- 가사·제목·아티스트명에 포함된 단어, 영상·표지 인물의 성별, 부정·불확실 표현을 구분한다. `남자`·`인디` 부분 문자열만으로 판정하지 않는다.
- 제외 범위는 문맥 단위로 적용한다. 예를 들어 영상 문장이 뒤에 붙어도 앞의 `남자 인디 노래` 단서는 유지하고, `남자 보컬이고 장르는 모르겠어`의 장르 불확실성이 성별까지 지우지 않도록 한다. 따옴표도 일괄 삭제하지 않는다. `장르는 '인디'야`는 명시 단서다.
- 기존 문맥 추출 유틸리티는 동작을 확인한 뒤 활용한다. 재질문 수정 때문에 검색 분석 규칙을 전역 변경하지 않는다.
- `QueryAnalysis`의 검색용 `genre`, `vocal_gender`, 태그, 검색문 및 분석 프롬프트를 바꾸지 않는다. `인디`를 임의의 검색 장르로 매핑하지 않는다.

② 질문 선택 규칙 공통화

- `pick_data_question()`에 `known_slots`를 전달할 통로를 추가한다. 제외 대상은 `set(asked_slots) | set(known_slots)`이다.
- `pick_question()`도 같은 공통 판정으로 `known_slots`를 얻어 동일한 선택 함수를 호출한다. 출생 연도 질문의 우선순위는 유지한다.
- `_can_ask_data_question()`은 남은 슬롯을 같은 기준으로 계산한다. `/search`의 `clarify_deferred`와 `/search/clarify` 모두 이 판단을 사용한다.
- 두 데이터 슬롯을 이미 알면 `/search`는 `clarify_deferred=false`를 보낸다. 직접 `/search/clarify`를 호출해도 질문은 null이며 후보 `fetch()`를 하지 않아야 한다. 의존성 객체 생성 자체와 실제 조회 호출은 구분해서 검증한다.
- 단서가 하나만 있으면 나머지 슬롯에 기존 후보 coverage/discrimination 조건을 적용한다. 슬롯·턴·거절 한도는 실제 이력만으로 기존대로 센다.

③ 화면과 주변 호출부 연결

- `SearchResponse`, `ClarifyRequest`, `map.js`의 저장·전송을 함께 갱신한다.
- 출생 연도 답 후 재검색은 최신 후보와 그 응답의 `known_slots`를 사용한다. 출생 연도 질문 닫기·건너뛰기에서도 원문 단서가 사라지지 않아야 한다.
- 새 검색은 기존 단서와 받아 둔 질문을 초기화한다. 결과가 바뀌면 질문 캐시를 무효화하고, 늦은 옛 응답은 기존 `searchSeq` 보호로 버린다.
- 질문 null이면 기존 `submitTurn(null)`로 한 번만 진행한다. 이미 구현된 조회 실패·시간 초과 시 거절 진행도 유지한다.
- `demo_rehearsal._clarify_body()`, 모의 서버 왕복, 프론트 테스트의 요청 본문 등 실제 질문 API 호출부를 함께 수정한다. 새 정책 때문에 질문이 불필요해진 시나리오는 무조건 질문이 있어야 성공하는 리허설을 유지하지 말고, 질문할 정보가 남은 전용 시나리오로 검증한다.
- `evaluate_clarification.py`의 `pick_question()` 경로도 같은 정책을 사용하게 한다. 실제 서비스만 고치고 평가 하네스는 이전 정책을 쓰는 상태를 남기지 않는다.

④ 과거 정책과 설명 정리

- `test_asks_again_even_when_the_user_already_said_it`을 새 요구사항을 검증하는 테스트로 교체한다. 단순 삭제로 끝내지 않는다.
- `clarify.py`의 설명, `stated_in_query()`의 역할, 후보만 있으면 질문할 수 있다고 적힌 API·테스트 주석을 최종 설계에 맞춘다. 사용하지 않는 헬퍼는 제거하거나 새 공통 함수로 정리한다.
- 테스트 fixture의 `original_query`와 분석값을 일치시킨다. 현재 `_analysis()`의 기본 원문은 `비 오는 날 발라드`이므로, 장르 미지정 테스트에 그대로 쓰면 새 규칙을 잘못 검증하게 된다.

| 화면 | 연도 답·닫기 뒤 유지, 새 질의에서 초기화, 늦은 응답 무시, 질문 재사용과 무효화, null·실패 시 거절 검색 1회. |
| 검색 영향 | 동일한 원본 분석에서 검색 라우터 입력·명시적 answers가 전후 동일. 질문 정책 변경 때문에 검색 단서나 가짜 답변이 생기지 않음. |

우선 실행할 로컬 회귀 테스트:

```sh
venv/bin/python -m pytest tests/test_clarify_question.py tests/test_clarify_deferred.py tests/test_clarify_state.py tests/test_clarify_birth_year.py tests/test_clarify_harness.py tests/test_clarify_answers_for_reranker.py tests/test_demo_faults.py tests/test_frontend_node.py -q
```

새 판정 테스트 파일을 별도로 만들었다면 위 대상에 포함한다. 이후 전체 `pytest tests/ -q`를 한 번 실행한다. 기존 경로 테스트 문제가 현재 환경에서도 발생한다면 원인을 확인해 별도 보고한다. 과거 실패라는 이유만으로 새 실패를 무시하지 않는다.

실제 서버·유료 모델 없이도 위 계약과 정책을 검증할 수 있다. 구현 완료를 위해 전체 검색 성능 평가를 먼저 돌릴 필요는 없다. 실제 브라우저 점검에서는 두 사용자 예시로 연도 답/건너뛰기와 거절 버튼 동작을 확인하되, API·DB 사용 여부를 결과에 구분해 적는다.

7. 효과 해석과 완료 기준

필수 목표는 위 명시 단서 사례에서 중복 질문이 0건이고, 필요한 질문 및 질문 없는 거절 진행이 유지되는 것이다. 실제 질의 전체에서의 재질문 정확도나 검색 정확도가 100%가 된다는 의미는 아니다.

이전 오기억 평가의 c701·c705·q101처럼 최초 성별이 틀린 질의는 회수 성능이 낮아질 수 있다. 이를 숨기거나 오라클 결과를 맞추려고 중복 질문을 다시 넣지 않는다. 평가가 필요하면 같은 설정·같은 질의에서 재질문 슬롯, 거절만 진행한 횟수, 최종 Hit@10을 함께 비교한다. 첫 검색 순위와 재질문 후 순위는 구분한다.

완료 보고에는 변경 파일, 사용자 예시의 실제 선택 결과, 반례와 상태 테스트 결과, 수행하지 않은 검증, 남은 제약을 적는다. 커밋·푸시·PR 생성은 하지 않는다. 연도 휠 UI, 유명도 보충, 후보 생성·리랭킹, 크롤러·데이터·색인은 이번 변경 범위에서 제외한다.
