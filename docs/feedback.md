# 정답 피드백 — 수집 · 검토 · 색인 · 검색 재사용

결과 곡 오른쪽의 **정답** 버튼(**근거** 옆)을 누르면 사유를 적고 정답을 제출할 수 있다(사유는 선택 입력).
운영자가 그 제출을 검토해 승인하면, 승인 사례가 다음 유사 질의에서 **후보를 보충**한다.

| 단계 | 내용 | 상태 |
|---|---|---|
| ①~② 수집 | 검색 기록·제출 권한·정답 선택·사유·수정·철회 | 병합(#47·#50) |
| ③-A 검토 | 검토 계약(대기·승인·보류·제외) + 로컬 전용 검토 화면 | 구현(이 문서) |
| ③-B 색인·정리 | 승인 사례를 전용 Qdrant 컬렉션에 색인, 만료·무효 사례 자동 정리 | 구현(이 문서) |
| ④ 후보 보충 | 유사 사례 조회 → 최신 상태 확인 → 최종 후보 절단 전 합류 | 구현, **기본 꺼짐** |
| ⑤ 비교 평가 | off/on 비교 도구 · 유사도 보정 · 합성 자료 기능 확인 | 도구 완성, **실자료 품질 측정은 미수행** |

**하지 않는 것.** 자동 승인·자동 학습, 리랭커에 사유·검토 문장 전달(⑤′), 후보 밖 정답 등록(⑥),
곡 메타데이터·곡 컬렉션·BM25 통계 수정, 원격 관리자 인증.

## 1. 스위치

세 스위치는 **서로 독립**이고 모두 기본 꺼짐이다. 셋 다 꺼져 있으면 Mongo 연결·임베딩·Qdrant 조회가 생기지 않는다.

| 환경 변수 | 켜면 | 프로세스 |
|---|---|---|
| `FEEDBACK_COLLECTION_ENABLED=1` | 검색 기록 저장·제출 권한 발급·제출 API | 검색 서버 |
| `FEEDBACK_INDEX_WORKER_ENABLED=1` | 승인 사례 색인 + 만료·무효 사례 정리(주기 작업) | 검색 서버 |
| `FEEDBACK_RETRIEVAL_ENABLED=1` | 검색 후보 보충 | 검색 서버 |

- 수집을 꺼도 색인 작업은 돈다 — **쌓인 자료의 만료 정리가 수집 스위치에 묶이지 않는다.**
- 검색 반영을 꺼도 수집·검토·색인은 그대로다(품질 기준을 넘기 전의 운영 상태).
- `FEEDBACK_EVIDENCE_ENABLED`는 후속(⑤′) 예약 이름이다. **읽는 코드가 없다.**
- 검토 화면은 별도 프로세스이고 스위치가 없다(띄우면 동작한다). §4.

숫자 설정은 비었거나, 숫자가 아니거나, `nan`·`inf`이거나, 범위를 벗어나면 **기본값**으로 읽는다
(잘못 적은 값이 문턱을 풀어 넓은 사례를 들이지 않게). 경고는 값마다 한 번 로그에 남는다.

## 2. 수집

기존 MongoDB 설정(`MONGO_URI`, `MONGO_DB_NAME`)에 아래 값을 더하고 서버를 다시 시작한다.

```dotenv
FEEDBACK_COLLECTION_ENABLED=1
FEEDBACK_CORPUS_VERSION=corpus5143-20261012-bm25-bf606b19ab02
```

코퍼스 값은 예시다. 실제 배포판을 적는다(없으면 `unknown`).
수집을 켜면 성공한 검색의 표시 결과를 저장하고 응답의 `feedback`에 `search_id`와 제출 토큰을 발급한다.
Mongo 장애·빈 검색 결과일 때는 `feedback=null`이며 제출 버튼이 없다. 검색은 그대로 응답한다.
DB 작업에는 750ms 시간 예산을 적용하고, 실패하면 30초 동안 저장소를 다시 두드리지 않는다.

| 컬렉션 | 내용 |
|---|---|
| `search_runs` | 서버가 실제 표시한 곡·순위, 후보 목록, 질의·검색 분석·재질문 맥락, 실행 연결, 코드·분석기·코퍼스·리랭커 정보, `feedback_supplement`(§6) |
| `search_feedback` | 실행당 현재 선택 한 건, 사유, `pending/withdrawn`, `revision`, 제출 이력 + 검토·색인 기록(§3·§5) |
| `feedback_ops_status` | 색인 작업의 마지막 주기 요약 한 건(건수·시각·오류 코드). 원문 없음 |

토큰은 검색 응답을 받은 화면의 메모리에만 둔다. 서버에는 SHA-256 해시만 저장한다.
브라우저 출생 연도 원값과 해당 재질문 답은 저장하지 않고 실제 검색에 쓴 시기 창만 남긴다.
원질의 자체에 사용자가 적은 개인 정보는 원문에 남을 수 있으므로 원문 컬렉션을 공개하거나 평가 자료로 그대로 내보내지 않는다.

### 제출 API

`POST /api/v1/feedback` — 계약은 #47과 같다. **응답의 `status`는 `pending`/`withdrawn`뿐이고 검토 상태를 싣지 않는다.**

```json
{
  "search_id": "서버 응답의 32자리 ID", "token": "서버 응답의 제출 토큰",
  "submission_id": "클라이언트가 만든 제출별 무작위 ID", "expected_revision": 0,
  "action": "select", "selected_song_id": "표시된 곡 ID", "reason": "도입부의 휘파람 소리로 알아봤어요."
}
```

- `reason` 최대 1,000자. 선택하지 않은 곡을 오답으로 저장하지 않는다.
- 같은 `submission_id` 재시도는 한 번만 저장된다. 다른 제출이 경합하면 `revision` 조건으로 한 건만 반영하고 뒤 요청은 409.
- 철회는 `action=withdraw`, `selected_song_id=null`, `reason=""`. 검색당 20회까지 수정, 그 뒤에도 마지막 철회는 가능.
- 다른 검색의 토큰·만료된 검색 404, 표시하지 않은 곡 422, 수집 꺼짐·DB 장애 503.

## 3. 검토 계약

`search_feedback` 문서에 검토 필드를 더했다. 기존 문서(`review=null`, 검토 판 필드 없음)는 **대기**로 읽는다.

| 필드 | 뜻 |
|---|---|
| `revision` | 사용자 제출 판. 선택·사유를 바꾸거나 철회하면 오른다(기존) |
| `review_version` | 검토 판. 운영자가 저장할 때마다 오른다(문장만 고쳐도, 승인을 취소해도). **사용자 수정으로 되돌리지 않는다** |
| `review` | `state`(`approved`/`on_hold`/`rejected`/`pending`) · `source_revision` · `version` · `reviewed_by` · `reviewed_at` · `note` |
| `reusable_text` | 운영자가 쓴 재사용 단서(최대 500자). 승인에는 비어 있지 않아야 한다 |
| `review_history` | 결정 이력 최근 20건(상태·판·시각만, 문장 없음) |
| `index` | 색인 기록: `state`(`pending`/`indexed`/`failed`) · 판 · `embedding_version` · 재시도 정보 |

**세 주체가 한 문서를 조건 갱신한다.** 서로를 덮어쓰지 않는다.

- 사용자 제출 — `revision` 일치 조건. 선택이 바뀌면 `review`·`reusable_text`·`index`를 비운다(승인 무효 → 재검토).
- 운영자 검토 — `revision` + `review_version` 일치 + 활성 제출 + 미만료를 **한 번의 `find_one_and_update`** 조건으로 건다.
  사용자 수정·철회나 다른 검토가 먼저 들어갔으면 409와 최신 문서를 돌려준다. 만료된 사례는 410.
  저장은 됐는데 응답을 잃은 뒤 같은 내용으로 다시 보낸 요청은 한 번만 반영된 것으로 본다.
- 색인 작업 — `revision` + `review_version` 일치 + 승인 상태 조건. 늦게 끝난 예전 판 작업은 완료 표시에 실패한다.

"재사용할 수 있는 사례"의 판정은 한 곳(`src/feedback/review.py: reusable_case`)에 있고 검토 화면·색인·검색이 함께 쓴다:
문서 있음 · 활성 제출 · 미만료 · 승인 · 검토가 최신 제출 판을 봤음 · 검토 판 일치 · 문장과 선택 곡 있음.

**선택과 사실을 구분한다.** 선택은 "이 사용자가 찾던 곡과 질의의 연결"이지 사유의 모든 내용이 곡의 사실이라는 뜻이 아니다.
잘못 기억한 성별·개인 생애 단계·개인정보는 재사용 단서에 넣지 않는다. 정리할 단서가 없으면 보류·제외한다.

## 4. 로컬 검토 화면

```sh
venv/bin/python -m src.feedback.review_app      # http://127.0.0.1:8001/
```

| 환경 변수 | 기본값 | 뜻 |
|---|---|---|
| `FEEDBACK_REVIEW_HOST` | `127.0.0.1` | loopback 주소만 받는다. 다른 값이면 **뜨지 않는다** |
| `FEEDBACK_REVIEW_PORT` | `8001` | |
| `FEEDBACK_REVIEWER` | `local` | 검토 기록에 남길 이름. **로컬 설정값이며 확인된 신원이 아니다**(화면에도 그렇게 적는다) |

`MONGO_URI`·`MONGO_DB_NAME`은 검색 서버와 같은 값을 쓴다. 검색 서버가 떠 있어도, 꺼져 있어도 된다.

**공개 검색 서버에는 검토 API가 없다.** 별도 진입점(`src/feedback/review_app.py`)이고 인증이 없으므로 접근을 이 프로세스 안에서 좁힌다.

1. loopback에만 붙는다.
2. `Host` 헤더가 `127.0.0.1`·`localhost`·`[::1]`의 설정 포트가 아니면 403(DNS rebinding 방어).
3. API는 다른 사이트에서 온 요청을 받지 않는다(`Sec-Fetch-Site`, `Origin`이 이 화면의 출처와 다르면 403).
4. 쓰기 요청은 화면이 `/api/session`에서 받은 토큰(`X-Review-Token`)과 JSON 본문이 모두 있어야 한다.
   CORS 응답 헤더를 주지 않는 것만으로는 쓰기를 막지 못한다 — 브라우저는 단순 요청을 그대로 보낸다.
5. 모든 응답에 `Cache-Control: no-store`, CSP(`script-src 'self'`), `X-Frame-Options: DENY`.

화면:

- **목록** — 상태 필터(대기·승인·보류·제외·철회·전체), 쪽 이동, 선택 곡(검색 당시 제목·표시 순위), 사유 유무, 생성 시각, 남은 보관 기간, 색인 상태.
  목록 응답에는 원질의·사유 본문을 싣지 않는다. 만료된 사례는 어느 목록에도 없다. 만료가 가까운 것부터 보인다.
- **상세** — 원질의, 재질문 맥락(턴·답변·거절한 곡·검색에 쓴 시기 창), 선택 곡과 표시 당시 순위, **현재** 곡 정보(Mongo `songs`),
  사용자 사유, 생성·만료 시각과 남은 기간, 검토 결과와 이력.
- **편집** — 재사용 단서·검토 사유, 승인·보류·제외·대기로 되돌리기.
  - 충돌(409)하면 최신 문서를 다시 보여주고 **작성 중이던 입력은 지우지 않는다.** 확인 뒤 다시 저장한다.
  - 철회·만료된 사례는 입력과 버튼이 잠긴다. 화면을 열어 둔 사이 만료돼도 저장을 막는다.
  - 10자 미만의 단서에는 넓은 단서 경고를 보인다(막지는 않는다).
- **머리말** — TTL 준비 상태, 승인·색인 완료·실패 건수, 색인 작업의 마지막 성공 시각과 최근 오류, 만료 후 남은 문서 수.

검토 화면은 **Mongo만 읽고 쓴다.** 로컬 Qdrant 폴더는 한 프로세스만 열 수 있고 그 주인은 검색 서버다.
승인하면 같은 쓰기에서 `index.state="pending"`이 함께 기록되고, 검색 서버의 색인 작업이 그것을 보고 처리한다.

**단서를 쓰는 기준.** 질의와 사유에서 다음 검색에 다시 쓸 수 있는 단서만 직접 정리한다.
"슬픈 발라드"처럼 넓은 단서는 무관한 검색에도 걸린다 — **유사도 문턱으로는 걸러지지 않으므로 검토에서 거른다**(§6·§8).

## 5. 색인과 자동 정리

`FEEDBACK_INDEX_WORKER_ENABLED=1`이면 검색 서버 안에서 스레드 하나가 돈다(`src/feedback/worker.py`).
별도 worker 프로세스를 띄우지 않는다 — 로컬 Qdrant 폴더를 이미 열어 둔 검색 서버가 자기 클라이언트로 색인한다.

- 기동 직후 **바로 한 주기**(꺼져 있던 동안 밀린 색인·정리 처리), 그 뒤 `FEEDBACK_WORKER_INTERVAL_SECONDS`(기본 60)마다.
- 종료: 멈춤 신호 → 돌던 단계가 끝날 때까지 기다림(DB 호출 한 번의 예산은 5초) → 벡터 클라이언트 닫기 → Mongo 닫기
  (`src/backend/main.py` lifespan). asyncio 작업 취소로는 동기 스레드가 멈추지 않으므로 스레드가 끝나는 것을 기다린다.

| 환경 변수 | 기본값 | 범위 | 뜻 |
|---|---|---|---|
| `FEEDBACK_WORKER_INTERVAL_SECONDS` | 60 | 1~3600 | 주기 |
| `FEEDBACK_INDEX_BATCH` | 16 | 1~256 | 한 주기에 색인할 사례 수 |
| `FEEDBACK_EMBED_BATCH` | 8 | 1~64 | 한 번에 임베딩할 문장 수(검색과 KoE5 모델을 나눠 쓴다) |
| `FEEDBACK_SWEEP_BATCH` | 200 | 1~2000 | 한 주기에 대조할 포인트·문서 수 |
| `QDRANT_FEEDBACK_COLLECTION` | `vaguefinder-feedback-cases-1024-koe5` | | 사례 컬렉션 이름(뒤에 `__<네임스페이스>`가 붙는다) |

**컬렉션.** 곡 컬렉션과 분리된 전용 컬렉션. 포인트 하나 = 승인 사례 하나. 벡터는 **운영자가 쓴 재사용 문장**의
KoE5 임베딩(1024차원, E5 `passage: ` 접두사, L2 정규화 — 곡 텍스트와 같은 규약, 거리 COSINE).
페이로드는 `feedback_id` · `song_id` · `source_revision` · `review_version` · `embedding_version` · `expires_at_ts` · `expires_at` · `source`뿐이다.
**원질의·사용자 사유·재사용 문장 본문은 Qdrant에 복사하지 않는다.**
포인트 ID는 사례마다 정해진 UUID(`uuid5`)라 다시 올리면 덮어쓴다(중복 없음).

**한 주기**(`src/feedback/indexer.py`) — 한 단계가 실패해도 나머지는 계속한다.

1. **만료 포인트 삭제** — 포인트에 실린 `expires_at_ts`로 지운다. Mongo 원본이 TTL로 먼저 사라졌어도 지워진다.
2. **포인트 대조** — 포인트를 한 묶음 읽어 Mongo 최신 문서와 맞춘다. 원본 없음·철회·미승인·예전 판이면 **그 판의 포인트만** 지운다
   (판 번호가 조건이라, 그 사이 새 판이 올라왔으면 지워지지 않는다).
3. **색인** — 색인할 승인 사례(대기 · 재시도 시각이 된 실패 · 임베딩 판이 다른 완료)를 임베딩해 올린다.
   올리기 직전에 Mongo를 다시 읽고, 올린 뒤 완료 표시도 판 조건으로 건다. 그 사이 판이 바뀌었으면 방금 올린 포인트를 지운다.
4. **완료 대조** — Mongo에 완료로 적힌 사례가 Qdrant에 그 판으로 있는지 본다. 없으면 색인 대기로 되돌린다.
5. **Mongo 만료 문서** — TTL 색인이 준비되지 않았을 때만 만료 문서를 직접 지운다(§7).

- **Mongo를 읽지 못한 주기에는 포인트를 지우지 않는다**("문서 없음"과 "읽지 못함"을 구분할 수 없으므로).
- 실패는 `index.state="failed"`와 다음 시도 시각으로 남는다. 60초에서 시작해 두 배씩, 최대 1시간.
- 재시작 복구에 따로 할 일은 없다. 색인할 것은 문서의 `index` 기록에서, 지울 것은 포인트 대조에서 매 주기 다시 찾는다.
- 모델·입력 규약이 바뀌면 `src/feedback/settings.py`의 `EMBEDDING_VERSION`을 올린다. 예전 판 포인트는 검색에서 걸러지고 다시 색인된다.

**상태 확인.**

- `GET /health`의 `feedback` — `collection`(켜짐·TTL 상태·준비 여부) · `index_worker`(상태·주기 수·마지막 성공·오류 코드·마지막 주기 건수) · `retrieval`.
  상태 코드·건수·시각뿐이다. 원문·예외 본문·연결 정보는 없다.
- 검토 화면 머리말과 `GET /api/status` — Mongo `feedback_ops_status`에 남긴 마지막 주기 요약.
- 오류 코드: `mongo_unavailable` · `qdrant_error` · `embedding_error` · `worker_unavailable`. 로그에는 예외 **종류**만 남는다.

## 6. 검색 후보 보충

`FEEDBACK_RETRIEVAL_ENABLED=1`일 때만 돈다. 꺼져 있으면 라우터는 스위치만 읽고 아무것도 부르지 않는다.

```
질의 임베딩 → Qdrant 유사 사례(미만료·같은 임베딩 판·문턱 이상) → 사례가 가리키는 곡의 현재 정보
  ── 기존 검색 경로와 나란히 ──
→ [후보에 합치기 직전] Mongo 최신 문서 일괄 조회 → 활성 제출·승인·제출 판·검토 판·미만료 확인
→ 거절한 곡·삭제된 곡·곡 색인에 제목이 없는 곡 제외, 같은 곡의 사례는 가장 가까운 것 하나로
→ 보충이 없을 때의 최종 후보를 계산 → 그 밖의 곡만 진입 판정용 점수로 융합 목록에 넣음
→ 명시 단서 보정 → 거절 제외·절단(후보 수 그대로) ── 여기서 절단을 넘은 곡만 "들어온 곡"
→ 들어온 곡이 보충 없는 최종 후보 순서(답변 보너스 반영)의 끝자리를 그 수만큼 대신함 → 리랭커
```

- **질의문**은 검색이 실제로 쓴 분석으로 만든다(`build_case_query`): `search_text`(생애 단계 표현 제외) + 가사 의미 단서 +
  지금 유효한 재질문 답(성별·장르·형태·시기). **출생 연도는 넣지 않는다.**
- **상태 확인 시점은 후보에 합치기 직전의 Mongo 조회 한 번이다.** 만료는 그 조회가 끝난 시각으로 다시 본다.
  그 뒤(융합·리랭킹 중)의 철회·수정·승인 취소·만료는 진행 중이던 그 요청에는 반영되지 않고 **다음 검색부터** 빠진다.
  Qdrant 포인트가 아직 남아 있어도, 늦은 색인 작업이 예전 판을 다시 올렸어도 여기서 걸러진다.
- **Mongo를 읽지 못하면 사례를 하나도 쓰지 않는다.** Qdrant에 남은 값만 믿고 보충하지 않는다.
- **보충은 후보 밖 곡에만 한다.** 보충 없이도 최종 후보인 곡은 점수를 건드리지 않는다 — 첫 버전의 피드백은 후보에 넣는 것까지이고
  기존 후보의 순위를 올리는 신호가 아니다.
- **들어오는지는 보정까지 본 점수로 정한다.** 후보 밖 곡은 밀려날 꼬리 후보 가운데 가장 앞선 곡의 보정 전 융합 점수 ×
  `FEEDBACK_FUSION_WEIGHT`를 받고, 명시 단서 보정을 기존 후보와 똑같이 받은 뒤 절단을 넘어야 들어온다. 질의가 말한
  성별·장르·제목과 맞지 않아 보정이 그 곡보다 적으면 **들지 못한다**(자리를 보장하지 않는다). 고정 RRF 가중을 쓰지 않는 이유:
  경로 가중이 질의마다 달라(텍스트 0.5~1.0) 고정 가산은 같은 사례라도 질의의 경로 가중에 따라 진입 여부가 갈린다.
- **들어온 곡의 자리는 후보의 끝이다.** 진입 판정에 쓴 점수로 줄을 세우지 않는다 — 보정 한 번(1/61)이 후보 30곡의 융합 점수
  폭과 비슷해서, 그대로 두면 질의에 성별·장르가 있을 때 보충 곡이 "단서가 맞는 묶음" 안으로 올라간다. 들어온 곡은
  **보충 없는 최종 후보 순서(재질문 답변 보너스까지 반영)의 끝자리를 그 수만큼 대신한다.** 그래서 보충을 켰을 때 달라지는 것은
  **끝자리뿐**이고, 나머지 후보의 점수·순서와 리랭커 입력 순서는 보충이 없을 때와 같다. 들어온 곡에는 답변 보너스를 주지 않고,
  낮춘 점수는 근거 패널에 `이전 사용자 제보로 들어온 곡은 후보 끝에 배치` 조정으로 남는다(경로 기여 + 가감점 = 검색 점수).
  (리랭커 입력이 같다는 것은 보충이 없어도 리랭킹을 하던 요청에 한한다. 기존 후보가 1곡뿐이라 리랭킹 대상이 아니던 요청은
  보충으로 후보가 늘면 리랭커가 새로 불린다.)
- **배경 지식(Context) 경로와 함께 돌 때도 같다.** Context 경로는 보충보다 먼저 융합되므로 보충이 보는 "기존 후보"에 이미 들어 있다.
  응답에 싣는 Context 사실(`context_hits_out`)은 **끝자리를 바꾼 뒤의 최종 후보** 기준으로 모은다 — 밀려난 곡의 사실은 실리지 않고,
  보충으로 들어온 곡이 Context 경로에도 걸렸으면 그 사실은 실린다. 보충이 없으면 절단 직후의 후보와 같은 집합이다.
- **보충 곡은 리랭커 없이는 표시되지 않는 자리에만 선다.** 한 검색의 보충 수는 `FEEDBACK_SUPPLEMENT_SONGS`와
  **후보 수 − 표시 수** 가운데 작은 쪽이다(서비스 설정 30·15면 3). 후보 수 = 표시 수면 보충하지 않고, 기존 후보가 표시 수보다
  적을 때도 하지 않는다(끝에 세워도 표시 구간 안이다). 그래서 리랭킹이 꺼졌거나, 정책으로 생략됐거나, 실패해 후보 순서가
  그대로 나가는 요청의 표시 결과는 보충이 없을 때와 같다 — 보충 곡을 표시 구간으로 올리는 것은 리랭커뿐이다.
- **전제: 리랭커가 후보 끝까지 평가해야 효과가 있다.** 보충 곡은 후보 끝에 서므로, 리랭커가 후보 앞쪽만 평가하는 설정에서는
  들어와도 평가받지 못해 표시될 수 없다(그때도 상태는 `applied`, 들어온 곡 수는 그대로 기록된다). 해당하는 경우:
  `GEMINI_RERANK_MAX_CANDIDATES`(기본 30, 범위 10~50)가 후보 수보다 작을 때 · CE에 `RERANKER_SCORE_TOP_N`을 준 측정 ·
  `candidate_k`를 30보다 크게 준 요청과 측정. **서비스 기본(후보 30 · listwise 평가 30)은 해당하지 않는다.**
  이 설정들을 바꿀 때는 보충이 꺼진 것과 같아질 수 있음을 함께 본다.
- 같은 곡의 제출이 여러 건이어도 점수가 쌓이지 않는다. 재질문에서 거절한 곡은 보충하지 않는다.
- **최종 순위는 기존 리랭커가 곡 정보만 보고 정한다.** 재사용 문장·사용자 사유는 리랭커에 가지 않는다
  (검색은 사유를 Mongo에서 읽지도 않고, 재사용 문장은 비어 있지 않은지만 본다).
- 가중치를 고정한 ablation(`force_weights`)과 보정을 끈 실행(`disable_boost`)에는 넣지 않는다.
- 기존 가사 exact 보호·거절 필터·명시 단서 보정·재질문·MV 정책은 그대로다.
- 요청 시간 기록: 조회는 `path.feedback_cases`, 합치기 직전의 대기는 `search.feedback`. 이 대기는 `search.fuse` 구간 안에 있으므로
  조회한 요청의 `search.fuse`에는 `feedback_wait_ms`가 함께 적힌다(융합 자체가 느려진 것으로 읽지 않게).

| 환경 변수 | 잠정값 | 범위 | 뜻 |
|---|---|---|---|
| `FEEDBACK_TOP_CASES` | 20 | 1~100 | Qdrant에서 읽을 유사 사례 수 |
| `FEEDBACK_SUPPLEMENT_SONGS` | 3 | 1~10 | 한 검색에서 보충할 곡 수 상한(후보 밖 곡 기준). 실제 상한은 이 값과 후보 수 − 표시 수 중 작은 쪽 |
| `FEEDBACK_MIN_SIMILARITY` | 0.65 | 0~1 | 질의와 사례 문장의 코사인 유사도 문턱 |
| `FEEDBACK_FUSION_WEIGHT` | 1.0 | 0 초과~2 | **진입 판정**에 쓰는 점수 = 꼬리 후보의 보정 전 융합 점수 × 이 값. 1보다 작으면 명시 단서 보정이 꼬리 후보보다 많아야 들어온다. 들어온 뒤의 자리(후보 끝)는 바꾸지 않는다 |
| `FEEDBACK_LOOKUP_BUDGET_SECONDS` | 0.6 | 0.05~5 | 기존 경로가 끝난 뒤 보충을 더 기다리는 상한(조회 + 상태 확인) |

표시 수를 따로 알려 주는 값(`RetrievalSettings.display_k`)은 **측정 전용이고 환경 변수가 아니다.** 기존 측정기처럼 후보 전체를
요청하는 호출(top_k = 후보 수)에서 실제 표시 수를 알려 주는 값인데, `evaluate_feedback_reuse harness`가 자기 프로세스 안에서만
정한다(`measurement_display`). 측정기와 서버가 같은 `.env`를 읽으므로 환경 변수로 받으면 서버에서도 후보 전체 요청의 표시 구간
보호가 풀린다 — 서버에는 이 값을 정할 길이 없다.

**모두 실험 전 잠정값이다.** 문턱 0.65의 근거는 합성 질의 10건 × 사례 14건뿐이다(§8). 실자료로 다시 정한다.

**실패하면 기존 후보로 간다.** 임베딩·Qdrant·곡 조회·Mongo 실패, 시간 초과, 유효 사례 없음, 융합 중 오류 —
어느 경우든 융합 점수와 곡 정보 캐시는 손대지 않은 그대로다(새 목록은 전부 계산된 뒤에만 반영한다).

**기록.**

- 내부 실행 기록(`SearchExplain.feedback`): 상태, 확인한 사례 수, 빠진 사유별 건수, 사례별 `feedback_id`·제출 판·검토 판·유사도·
  처리 결과(`added`/`already_candidate`/`over_limit`/`no_gain`)·진입 판정 점수, **들어온 곡(`entered_ids`)과 밀려난 곡(`displaced_ids`)**.
  평가 도구가 읽는다.
- 상태는 **실제로 들어온 곡이 있는지**로 정한다: `applied`(들어온 곡이 있다) · `not_entered`(유효한 사례는 있었지만 절단·상한·자리 때문에
  들어온 곡이 없다) · `already_in_candidates`(가리킨 곡이 모두 이미 후보였다) · `no_case` · `no_valid_case` · `timeout` · `failed`.
  응답 문구도 그에 맞춘다 — 들어온 곡이 없으면 "포함한 곡이 있습니다"라고 하지 않는다.
- 검색 기록(`search_runs.feedback_supplement`): 상태와 곡 ID(보충·진입·밀려남). 다른 사용자의 사례 ID는 남기지 않는다.
- **사용자 화면에는 출처만.** 제보로 들어온 곡의 짧은 설명은 **항상** 이 문장으로 시작한다 —
  "이전 사용자 제보를 참고해 후보에 포함한 곡이에요(제보 내용을 사실로 확인한 것은 아니에요)". 성별·장르·가사 단서가 맞는 곡이어도,
  다른 검색 경로의 기여가 남아 있던 곡이어도 같다(기존 검색만으로는 후보 밖이던 곡이다). 그 뒤에는 곡 자료와 맞는 단서를 사실로만 적는다
  ("여성 보컬 단서는 곡 정보와 일치해요"). 이 곡의 가산은 진입 판정에만 쓰였으므로 **"검색 점수에 반영"이라고 하지 않고**,
  단서 대조표의 근거 칸은 `후보에 드는 데만 쓰임 · 자리는 후보 끝(순위는 리랭커가 정함)`이다.
  점수 상세의 경로 기여에는 `이전 사용자 제보 참고`가, 응답의 곡별 기록에는 `feedback_entrant`가 실린다. 사례 ID·판·유사도·문장은 응답에 없다.

## 7. 30일 만료와 자동 삭제

**검색 기록 생성일부터 30일.** 원문·선택·사유·수정 이력·검토 결과·재사용 문장·벡터가 모두 원본 `search_runs.expires_at`을 물려받는다.
제출·검토·승인·수정·재색인으로 기간이 늘지 않는다.

| 대상 | 만료 판정 | 실제 삭제 |
|---|---|---|
| Mongo `search_runs`·`search_feedback` | 조회할 때마다 `expires_at > now` | TTL 색인(`expires_at`, `expireAfterSeconds=0`) |
| Qdrant 사례 포인트 | 조회 필터 `expires_at_ts > now` + 상태 확인 때 다시 | 색인 작업 1단계(주기마다) |

**TTL 준비 확인.** 기동할 때와 색인 작업이 주기마다 두 컬렉션의 색인을 실제로 읽어 상태를 남긴다(`/health`, 검토 화면).

| 상태 | 뜻 | 조치 |
|---|---|---|
| `ready` | `expires_at` TTL 색인(0초)이 있다 | — |
| `missing` | 색인이 없다 | 서버를 다시 띄우면 만든다. 권한이 없으면 `unauthorized`로 바뀐다 |
| `not_ttl` | 같은 키에 TTL이 아닌 색인이 있어 TTL 색인을 못 만든다 | 그 색인을 지우고 다시 띄운다 |
| `wrong_seconds` | `expireAfterSeconds`가 0이 아니다 | `collMod`로 0으로 바꾸거나 지우고 다시 만든다 |
| `unauthorized` | 색인 목록을 읽을 권한이 없다 | DB 사용자 권한(`listIndexes`·`createIndex`) |
| `unreachable` | 저장소에 닿지 못했다 | 연결 확인 |

- **TTL이 `ready`가 아니면 수집을 켰어도 `/health`의 `feedback.collection.ready`는 `false`다.** 수집 배포를 완료로 보지 않는다.
  검색 자체와 만료 판정(조회 시점)은 그대로 동작한다.
- 그동안 색인 작업이 켜져 있으면 **만료 문서를 직접 지운다**(TTL과 같은 조건 — 보관 기간을 줄이지 않는다).
  색인 작업도 꺼져 있으면 만료 문서가 남는다(검색·검토에는 쓰이지 않는다). 이 대체 수단은 TTL과 두 가지가 다르다:
  ① 기준 시계가 Mongo가 아니라 **검색 서버**다 — 서버 시계가 앞서 있으면 그만큼 일찍 지운다(NTP 동기화 전제).
  ② `expires_at` 색인이 없는 상태에서는 주기마다 두 컬렉션을 **전수 조회**한다(삭제와 남은 건수 세기). 30일치 자료에서는
  감당할 만하지만, 이 상태를 오래 두지 말고 색인을 고친다.
- **보고가 기동 시점 값에 굳지 않는다.** 색인 작업을 켜지 않은 서버도 검색 기록을 남길 때 10분 간격으로 색인 생성 명령을 다시 보낸다
  (같은 색인이 있으면 아무 일도 하지 않고, 지워졌으면 다시 만든다). 성공하면 보고가 `ready`로, 준비됐다고 적혀 있었는데 실패하면
  `unknown`으로 바뀐다. `/health`의 `feedback.collection.ttl_checked_at`이 마지막 확인 시각이다.
- Mongo TTL 삭제는 Qdrant에 전파되지 않는다. 포인트는 색인 작업이 지운다 — **색인 작업을 끄면 만료 포인트가 남는다**
  (검색은 필터로 쓰지 않는다). 검색 반영을 끌 때도 색인 작업은 켜 두거나, 끄기 전에 한 주기를 돌린다.

**평가용 복사·캐시·내보내기에도 원래 만료를 적용한다.**

- 실사용 사례를 파일로 내보낼 때는 줄마다 `expires_at`을 싣는다. 평가 도구는 만료가 지난 줄을 읽지 않는다(`eval_cases.load_cases`).
  만료를 멈추거나 다시 설정해서 평가하지 않는다.
- 운영 사례(`--cases live`)로 잰 산출물에는 사례 ID·재사용 문장을 쓰지 않는다 — 곡 ID와 건수만 남는다.
- 오래 남길 회귀 자료는 **합성 사례**로 만든다(`experiments/feedback_reuse/synthetic/`). 장기 성과는 사례 식별자가 없는 집계로만 남긴다.
- **백업.** 실제 피드백이 든 Mongo 백업·Qdrant 폴더 사본은 30일을 넘겨 보관하지 않는다. 복구했다면 검색 반영을 켜기 전에
  ① 만료 문서가 지워졌는지(`search_runs`·`search_feedback`의 `expires_at <= now` 0건 — 검토 화면 머리말의 "만료 후 남은 문서")
  ② 색인 작업이 한 주기 돌았는지(`/health`의 `index_worker.last_report.expired_points_remaining = 0`) 확인한다.
  Qdrant 폴더만 옛 사본으로 되돌린 경우 색인 작업이 포인트 대조로 무효 포인트를 지우고 빠진 사례를 다시 올린다.

- `harness`가 돌릴 수 있는 측정기: `evaluate_search_accuracy` · `evaluate_clarification` · `trace_candidate_drop`.
  이 측정기들은 라우터에 **후보 전체**를 요청하고(top_k = candidate_k) 자기 쪽에서 리랭킹해 상위 N곡만 쓴다. 보충 곡은
  "표시 수 뒤의 자리"에만 서므로, harness가 그 N을 라우터에 알려 준다(프로세스 안의 값, 환경 변수 아님) — 기본은 측정기 인자의
  `--top-k`(없으면 10), 다르게 주려면 `harness --display-k N`(1~100, 벗어나면 측정 전에 멈춘다).
  **검색 반영을 켠 뒤의 측정도 harness로 한다**(`--cases live`). 측정기를 직접 돌리면 표시 수를 알 수 없어 보충이 0건이다 —
  서비스는 on인데 측정값은 off와 같아진다.
  사례 파일을 끼우는 것은 그 실행 동안만이다 — 끝나면(실패해도) 조회 서비스 팩토리·스위치·argv를 원래대로 돌려놓는다.
- `compare`는 질의 하나가 끝날 때마다 detail을 쓰고, 요약·점검표까지 쓴 **뒤에** 측정 스택을 닫는다. 닫다가 난 오류는 경고로만 남는다
  (다 잰 결과를 버리지 않는다).
- 측정은 `.env`에 `GEMINI_RETRIEVAL_BACKEND=api_key`를 두고 돌린다(기준선과 같은 경로). `rerank_failed_rows`가 0이 아니면 다시 잰다.

**채택 기준**(검색 반영을 기본으로 켜기 전에 모두 충족):

1. 기존 dev 116(v06 57 + v09 59) + v10 dev 60에서 **Hit@10 손실 없음** — `harness`로 on을 재고 같은 조건의 off와 질의별로 대조.
2. **거절 곡 재등장 0** — `compare --reject-check`.
3. **off 순위 변화 0** — 꺼졌을 때의 후보·점수·리랭커 입력은 시험으로 고정(`test_switch_off_makes_no_feedback_calls…`), 측정에서는 회차 간 후보 변화 0.
4. 사례와 **따로 쓴 질의**(또는 시간 분할 — 어느 시각 이전의 검색에서 나온 사례, 이후의 검색을 질의로)에서의 개선이 반복 변동보다 클 것.
   사례를 만든 원문의 재입력·단순 바꿔쓰기는 기능 확인이다.
5. 지연 증가가 off 대비 중앙값·p95 각각 1초 이내(초안).
6. 대조군에서 손실이 없을 것 — 비슷한 단서의 다른 곡 · 다른 단서의 같은 곡 · 잘못된 사유 · 넓은 단서.
7. 재질문 손실 없음 — `harness --module src.retrieval.evaluate_clarification`으로 on을 재고 같은 질의의 off(`results_clarify_v09`와 같은 조건으로 새로 잰 것)와 대조.

**봉인 test**의 질의·정답·파생 문장은 사례·색인·튜닝에 쓰지 않는다. 도구는 `--sealed-final` 없이 test 분할을 열지 않는다.
최종 설정이 정해지면 그 설정 하나로 off 1회 · on 1회를 재고(`harness … --split test --sealed-final`) 기존 봉인 결과와 같은 방식으로 합산해 보고한다.

### 합성 자료 기능 확인 (품질 근거 아님)

`experiments/feedback_reuse/synthetic/` — 합성 곡 402개 · 질의 10건 · 사례 14건(target 6 · 비슷한 단서의 다른 곡 2 · 다른 단서의 같은 곡 2 ·
잘못된 사유 2 · 넓은 단서 2). 실제 곡·실제 피드백과 무관하다(`make_synthetic.py`가 고정 난수로 만든다).
실제 KoE5와 실제 라우터로 돌고, 분석은 고정, 리랭커는 없다.

```sh
venv/bin/python -m src.retrieval.evaluate_feedback_reuse compare --synthetic --runs 2 --reject-check \
  --output-dir experiments/feedback_reuse/results_synthetic_v01
venv/bin/python -m src.retrieval.evaluate_feedback_reuse calibrate --output-dir experiments/feedback_reuse/results_synthetic_v01
```

결과(`results_synthetic_v01`, 2회 동일):

| | 후보 Recall@30 | Hit@1 | Hit@10 | Hit@15 | 지연 중앙값 | p95 |
|---|---|---|---|---|---|---|
| off | 0.4 | 0.2 | 0.2 | 0.3 | 29ms | 39ms |
| on | 0.8 | 0.2 | 0.2 | 0.3 | 40ms | 54ms |

- 후보 밖이던 정답 4곡이 후보 끝자리로 들어왔다(f01·f03·f04·f06). 순위 지표가 그대로인 것은 **리랭커가 없어서**다 —
  보충 곡은 후보 끝에 서고, 표시 구간으로 올리는 것은 리랭커뿐이다.
- 정답이 이미 후보였던 질의(f02)와 넓은 사례가 가리킨 곡이 이미 후보였던 질의(f07)는 바뀐 것이 없다.
- 문턱에 걸린 정답 1건(f05, 유사도 0.585 < 0.65)은 보충되지 않았다.
- **잘못된 사유로 승인된 사례 2건, 그리고 비슷한 단서의 다른 곡 사례 1건(두 질의에서)도 후보에 들어왔다**(끝자리 후보를 그만큼 밀어냈다).
  유사도로는 걸러지지 않는다 — 질의와 말이 같으면 0.74~0.85가 나온다. 검토에서 거르고, 순위는 리랭커가 정한다.
- 거절 곡 재등장 0 · 회차 간 off 후보 변화 0 · off와 on의 표시 결과(15곡) 동일 · 지연 증가 중앙값 11ms(메모리 Qdrant·로컬, 실행마다 몇 ms씩 달라진다 — 운영 지연의 근거 아님).
- 유사도 분포: 같은 곡을 따로 쓴 말로 가리킨 쌍 0.58~0.75(중앙값 0.69), 무관한 쌍 0.63 이하.

**이 결과로 검색 품질 개선을 주장하지 않는다.** 실제 승인 자료가 없고(수집 기본 꺼짐), 독립 질의 세트도 없다.
실자료 측정에 필요한 것: 수집·검토로 쌓인 승인 사례, 그 사례와 따로 쓴 질의(또는 시간 분할), 현재 코퍼스에서의 off 기준선.

## 9. 운영 순서와 복구

1. 수집을 켠다 → `/health`의 `feedback.collection.ready`가 `true`인지 본다(TTL 준비).
2. 검토 화면을 띄워 승인·보류·제외한다.
3. 색인 작업을 켠다 → `/health`의 `feedback.index_worker.last_success_at`과 검토 화면 머리말의 색인 완료 건수를 본다.
4. 평가 기준을 넘긴 뒤에만 검색 반영을 켠다.
5. 켠 뒤의 정확도·재질문 측정은 `evaluate_feedback_reuse harness --cases live`로 돌린다. 기존 측정기를 직접 돌리면
   `.env`에서 검색 반영이 켜져 있어도 보충이 0건이라 off와 같은 값이 나온다(§8 평가 도구).

| 증상 | 확인 | 조치 |
|---|---|---|
| 승인했는데 색인 완료가 0 | 검토 화면 "색인 작업 기록 없음" | 검색 서버에 `FEEDBACK_INDEX_WORKER_ENABLED=1`이 있는지. 로컬 Qdrant는 서버가 떠 있어야 색인된다 |
| `last_error=qdrant_error` | 컬렉션 설정이 다르거나(차원·거리) 저장소 오류 | 로그의 예외 종류 확인. 사례 컬렉션은 지워도 된다 — 다음 주기에 완료 대조가 색인 대기로 되돌려 다시 올린다 |
| `last_error=embedding_error` | KoE5 로딩·추론 실패 | 모델 캐시·메모리. 사례는 `failed`로 남고 60초~1시간 간격으로 다시 시도한다 |
| `last_error=mongo_unavailable` | Mongo 연결 | 그 주기에는 포인트를 지우지 않는다. 연결이 돌아오면 다음 주기에 이어서 처리한다 |
| 만료 후 남은 문서가 줄지 않음 | TTL 상태(§7) | `not_ttl`·`wrong_seconds`·`unauthorized` 조치. 색인 작업이 켜져 있으면 직접 지운다 |
| 검색이 느려짐 | 요청 시간 기록의 `search.feedback`·`path.feedback_cases` | `FEEDBACK_LOOKUP_BUDGET_SECONDS`를 줄이거나 검색 반영을 끈다. 예산을 넘긴 조회는 버리고 기존 후보로 간다 |
| 보충을 즉시 멈춰야 함 | — | `FEEDBACK_RETRIEVAL_ENABLED=0`으로 다시 띄운다. 색인 작업은 켜 둔다(만료 포인트 정리) |

## 10. 남은 제한

- 품질 개선은 측정하지 않았다(§8). 문턱·가중·곡 수·시간 예산은 잠정값이다.
- 넓은 단서·잘못 승인된 사례는 검색 쪽에서 걸러지지 않는다. 검토 품질에 달려 있다.
- 보충의 효과는 **리랭커가 후보 끝까지 평가할 때만** 난다(§6의 전제). 리랭킹을 끄거나, 리랭커가 실패하거나, 정책으로 생략되거나,
  평가 범위가 후보 수보다 작으면 보충 곡은 표시되지 않는다 — 그런 요청에서 이 기능은 아무것도 바꾸지 않는다.
- 검토 화면에 인증이 없다. 로컬 전용이며 원격 접근은 인증을 갖춘 뒤의 별도 작업이다.
- 색인 작업은 프로세스당 하나다. 서버형 Qdrant에 검색 서버를 여러 개 붙이면 작업도 여러 개 돌지만,
  포인트 ID가 정해져 있고 삭제·완료 표시가 판 조건이라 결과는 같다(같은 사례를 중복해 임베딩하는 비용은 든다).
- 후보에서만 고르게 하므로 이미 찾은 곡의 사례만 쌓인다. 후보 밖 정답 등록(⑥)과 사유의 리랭커 전달(⑤′)은 후속이다.
- `search_feedback`에 상태별 색인을 만들지 않았다. 30일치 자료에서는 전수 조회로 충분하다고 보았고, 건수가 커지면 `review.state`·`index.state` 색인을 더한다.
