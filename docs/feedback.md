# 정답 피드백 수집

결과 곡에서 **찾던 곡이에요**를 누르면 사유를 적고 정답을 제출할 수 있다. 사유는 선택 입력이다.
같은 검색의 정답을 바꾸거나 철회할 수 있고, 저장에 실패하면 입력을 유지한다.

이 변경은 `NEXT_WORK` §2-22의 **① 검색 기록·저장 계약, ② 정답 선택·사유 UI**에 해당한다.
제출된 자료는 `pending`으로 쌓인다. 검토·Qdrant 색인·후보 보충·리랭커 연결은 아직 구현하지 않았다.
검색 순위·곡 메타데이터·기존 `community_feedback`에는 반영하지 않는다.

## 실행

기존 MongoDB 설정(`MONGO_URI`, `MONGO_DB_NAME`)에 아래 값을 더하고 서버를 다시 시작한다.

```dotenv
FEEDBACK_COLLECTION_ENABLED=1
FEEDBACK_CORPUS_VERSION=corpus5143-20261012-bm25-bf606b19ab02
```

코퍼스 값은 예시다. 실제로 사용하는 배포판을 적는다. 없으면 `unknown`으로 기록된다.
기본값은 `FEEDBACK_COLLECTION_ENABLED=0`이며, 꺼져 있으면 기록을 저장하거나 Mongo 연결을 만들지 않는다.
평가할 때도 기본값을 유지한다. 새 워크트리에는 테스트용 `map_data.json` 사본만 준비했다.
원래 작업 폴더의 `.env`·Qdrant·원본 수집 데이터는 복사하지 않았다.

수집을 켜면 성공한 검색의 표시 결과를 저장하고 응답의 `feedback`에 `search_id`와 제출 토큰을 발급한다.
Mongo 장애·빈 검색 결과일 때는 `feedback=null`이며 제출 버튼이 없다. 검색은 그대로 응답한다.
DB 작업에는 750ms 시간 예산을 적용한다. 초기 색인 생성이 그 시간을 넘기면 해당 검색의 수집은 생략하고 다음 요청에서 재시도한다.
파일 읽기·해시·스냅샷 생성·DB 기록은 작업 스레드에서 처리한다. 제출 권한은 기록 저장 뒤에 발급하므로,
검색 응답은 여전히 수집 완료를 기다린다. 수집을 켠 지연 측정에는 이 시간이 포함된다.

## 저장과 보관

| 컬렉션 | 내용 |
|---|---|
| `search_runs` | 서버가 실제 표시한 곡·순위, 후보 목록, 질의·검색 분석·재질문 맥락, 대화/직전 실행 연결, 코드 지문·분석기·코퍼스·리랭커 정보 |
| `search_feedback` | 실행당 현재 선택 한 건, 사유, `pending/withdrawn`, revision, 제출·수정·철회 이력 |

둘 다 **검색일부터 30일** 뒤 만료하며 `expires_at` TTL 색인으로 삭제한다. Mongo TTL 청소는 지연될 수 있으므로,
API도 만료를 직접 검사한다. 수정해도 보관 기간은 늘리지 않는다. 철회는 재사용 대상에서 빼는 것이며 원문·이력은 만료 때 함께 지워진다.
브라우저 출생 연도 원값과 해당 재질문 답은 별도 저장하지 않고 실제 검색에 쓴 시기 창만 남긴다.
원질의 자체에 사용자가 적은 개인 정보는 원문에 남을 수 있으므로 원문 컬렉션을 공개하거나 평가 자료로 그대로 내보내지 않는다.

토큰은 검색 응답을 받은 화면의 메모리에만 둔다. 서버에는 SHA-256 해시만 저장한다. URL·localStorage에 쓰지 않는다.
새로고침하면 제출 권한을 잃는다. 로그인·장기 검색 이력 화면은 이번 범위 밖이다.
재질문 요청은 `feedback_parent`로 직전 권한을 넘기며, 서버는 토큰과 같은 질의인지 확인하고 실행들을 연결한다.
이 값은 검색·랭킹 계산에는 들어가지 않는다.

## API

`POST /api/v1/feedback`에 검색 응답의 권한과 선택을 보낸다.

```json
{
  "search_id": "서버 응답의 32자리 ID",
  "token": "서버 응답의 제출 토큰",
  "submission_id": "클라이언트에서 만든 제출별 무작위 ID",
  "expected_revision": 0,
  "action": "select",
  "selected_song_id": "표시된 곡 ID",
  "reason": "도입부의 휘파람 소리로 알아봤어요."
}
```

- `reason`은 최대 1,000자다. 선택하지 않은 곡을 오답으로 저장하지 않는다.
- 응답에는 현재 선택·사유·상태·`revision`이 있다. 수정할 때 그 revision을 `expected_revision`으로 보낸다.
- 응답 유실 뒤 같은 내용은 같은 `submission_id`로 재시도한다. 한 번만 저장된다. 같은 ID의 내용을 바꾸면 409다.
- 서로 다른 제출이 경합하면 Mongo의 `_id` 유일성·revision 조건 갱신으로 한 건만 반영한다.
  뒤 요청은 현재 상태와 함께 409를 받는다. 화면은 자동으로 덮어쓰지 않고 다시 제출하게 한다.
- 철회는 새 제출 번호, 최신 revision, `action=withdraw`, `selected_song_id=null`, `reason=""`로 보낸다.
  최초 제출을 포함해 검색당 20회까지 바꿀 수 있으며, 그 뒤에도 마지막 철회는 가능하다.
- 수정 한도를 넘으면 409와 `detail.code=revision_limit`을 보낸다. 화면은 서버 안내를 표시하고 입력창·새 선택을 닫는다.
  철회는 계속 가능하며 새 검색에서는 다시 선택할 수 있다. 다른 수정 충돌의 재제출 흐름은 그대로다.
- 다른 검색의 토큰·만료된 검색은 404, 표시하지 않은 곡은 422, 수집 꺼짐·DB 장애는 503이다.
  저장 결과를 모르는 장애에서는 같은 제출 번호로 재시도한다.

## 검증과 후속 작업

`tests/test_feedback.py`는 저장·동시 제출·실행 연결·API·실패 격리를,
`tests/frontend/feedback.test.cjs`는 선택·입력·재시도·변경·철회·늦은 응답을 검증한다.
테스트는 격리된 저장소 대역을 사용하므로 실제 Mongo의 TTL 삭제·배포 권한은 배포 환경에서 별도 확인해야 한다.

2026-10-12 검증 결과:

- 피드백 백엔드 13건, 피드백 화면 상태 전이 8건 통과.
- 전체 회귀: **1,951 통과 · 7 건너뜀 · 2 제외**. 제외한 로컬 서버 타임아웃 테스트는 권한을 높여 별도 실행해 통과했다.
  나머지 하나는 기존 macOS `/tmp`와 `/private/tmp` 경로 비교 실패(`test_default_artifact_path_follows_custom_raw_sandbox`)다.
- 새 워크트리의 지도 파일 누락으로 실패했던 데모 테스트 6건은 `map_data.json` 사본을 준비한 뒤 통과했다.
- 실제 Chrome의 1280×900·390×844 화면에서 선택·사유 입력·저장·정답 변경·철회·새 검색 초기화를 확인했다.
  API·지도 데이터는 모의 응답을 사용했으며 브라우저 오류는 없었다. 캡처는 `/private/tmp/feedback-browser-results/`에 있다.
- `git diff --check`, 두 JavaScript 파일 문법 검사 통과. 운영 Mongo·Gemini·Qdrant를 호출한 검증은 하지 않았다.

PR #47 리뷰 반영 검증: 피드백 백엔드 14건과 프론트 테스트 실행기 1건(피드백 화면 10건·기존 화면 테스트 포함) 통과.
한도 응답의 오류 코드·화면 안내·선택 중단·철회·새 검색 초기화와, 파일 읽기/저장이 이벤트 루프 밖에서 실행되는 것을 추가 검증했다.

후속은 승인·제외·철회 처리와 색인 동기화 → 후보 보충 → 사유 전달 → 독립 질의 성능 평가 순서다.
현재 사용자는 선택을 수정할 수 있으므로, 후속 색인은 `feedback_id`에 해당하는 실행 ID와 revision을 함께 추적하고
수정·철회된 이전 판을 검색에서 제거해야 한다.
