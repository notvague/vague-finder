# Context 작품 단서 범위 수정 및 재검증

## 이번 피드백의 원인과 수정

현재 프로젝트와 `fresh_off_on` 피드백을 대조했다. 기존 test 32문항은
통과했지만 dev에서는 c701/c705의 Candidate@30 손실과 m104의 MRR@10
손실이 발생했다. 관계 표현이 `쓰인`으로 들어오면 작품 묘사 검사를
우회했고, 작품명이 있는 질의에서도 다른 작품의 프로필이 Context 후보로
합류할 수 있었다.

- `쓰인`, `쓰였던`, `사용된`, `나온`, `나오던` 등 외부 작품 사용 관계에
  같은 작품·장면 검사를 적용한다. 모델만 추출한 단서도 사용자가 말한
  구체적인 묘사를 유지한다.
- 작품명이 있는 질의는 같은 곡의 저장된 Dense 사실 또는 Sparse
  프로필에 그 이름이 있어야 Context 후보로 합류한다. 띄어쓰기,
  밑줄, 대소문자, 한글 조사는 처리하며 다른 제목의 접두사는 배제한다.
  별칭은 기존에 명시된 대응만 사용한다.
- Sparse 프로필의 `sparse_terms`를 기존 Qdrant payload에서 읽는다.
  이름 일치는 후보 검색의 조건이다. Sparse 일치 자체를 화면의 사실
  근거로 표시하지 않으며, Dense 근거는 관계·사건·출처 검사를 거친다.
- dev/test의 성능 손실이 있어도 같은 설정으로 추가 60문항과 10회
  재분석 진단을 모은다. 손실을 통과로 바꾸지 않는다. 입력·코퍼스·코드
  변경 또는 실행 오류는 계속 중단 사유다.

운영 검색 코드에는 평가 query_id·정답 song_id에 따른 분기가 없다.
합류 전 검사를 보완했으며 현재 병합된 SearchRouter, Qdrant backend,
클라이언트 종료·재시작 코드는 유지한다.

## 로컬 검증과 한계

현재 업로드한 코드 전체에서 Context, Qdrant backend, clarify, explain
회귀 검사를 실행했다: **3,772 passed, 32 subtests passed**.
여기에는 실제 메모리 Qdrant에 적재한 프로필 읽기, 잘못된 payload,
같은 이름의 다른 작품, 다른 곡의 근거, Sparse-only 표시 차단,
후보 수·중복·재질문 제외, 설치 전 해시 검사·백업·롤백 검사도 포함된다.

사용자가 보낸 로컬 Qdrant와 실제 KoE5/CLAP/Text BM25를 사용하고,
현재 실패 실행의 분석을 고정해 OFF/기존 ON/수정 ON을 비교했다.
리랭킹은 껐다. 아래 결과는 **저장된 분석으로 원인을 재현한 진단**이다.
새 Gemini 분석을 사용하는 전체 평가 또는 새 블라인드 평가를 대체하지 않는다.

| 문항 | 지표 | Context OFF | 기존 ON | 수정 ON |
|---|---|---:|---:|---:|
| c701 | Candidate@30 내 정답 순위 | 30 | 미진입 | 30 |
| c705 | Candidate@30 내 정답 순위 | 24 | 미진입 | 24 |
| m104 | Top-10 내 정답 순위 | 3 | 4 | 3 |
| c703 | Top-10 내 정답 순위 | 10 | 10 | 10 |
| nw001 | Top-10 내 정답 순위 | 미진입 | 8 | 7 |
| q203 | Candidate@30 내 정답 순위 | 미진입 | 28 | 22 |

q203은 여전히 Top-10 밖이다. nw008은 이번 고정 분석에서 수정 전후 모두
Candidate@30 밖이다. 이 수정이 모든 질의를 해결했다고 해석하지 않는다.
부분적인 실제 검색 재현에는 Gemini 호출과 MongoDB 원문 조회가 필요하지
않았으며, 가사 원문 경로·실제 HTTP API·전체 새 분석 평가는 사용자 환경에서
확인한다. 로컬 Python은 3.12이며 사용자 Docker Python 3.11과 구별한다.

## 적용 및 한 번에 재평가

수정 ZIP을 현재 프로젝트 루트에 풀고 PowerShell에서 실행한다.

```powershell
.\experiments\namuwiki\run_context_media_scope_fix.ps1 -Mode All
```

ZIP을 푸는 시점에는 기존 검색 파일을 통째로 덮어쓰지 않는다. 실행기가
현재 제공받은 소스의 정규화 SHA-256을 먼저 확인한 뒤 수정본을 설치한다.
줄바꿈/BOM 차이는 허용하고 다른 코드 변경은 보존한 채 중단한다. 원본
백업은 실행 결과 폴더의 `scope/backups/`에 남기며 쓰기 실패 시 변경분을
되돌린다. 이미 같은 수정이 적용된 경우 다시 적용하지 않는다.

현재 고정값을 유지한다:

```dotenv
CONTEXT_WEIGHT=0.5
CONTEXT_NAMED_MEDIA_MULTIPLIER=2.0
CONTEXT_FACT_K=100
CONTEXT_SPARSE_K=100
SEARCH_DEFAULT_CANDIDATE_K=30
```

실행기는 `.env`를 수정하지 않고 실제 검색 팩토리의 값을 확인한다.
추가 환경변수, 나무위키 재수집, 임베딩 재생성, Qdrant 재적재는 필요 없다.
기존 완전한 Context generation을 계속 사용한다.

진행 순서는 다음과 같다.

1. backend 중지 → 소스 확인·백업·설치 → Docker 빌드 → 코드 회귀 검사.
2. 실제 환경변수·인덱스 확인 → 새 분석으로 dev 74 / test 32 /
   이미 관측한 추가 60문항을 동일 분석의 Context OFF/ON으로 비교.
3. 사전 지정 10문항을 추가로 재분석해 변동성 확인. 이미지·오디오 경로는
   실제 실행 흔적으로 확인하며 평가기가 가중치를 강제로 바꾸지 않는다.
4. 전체 성능·근거 검사 통과 후 설정 적용 기록과 실제 HTTP API 검사를 수행.
5. 성공·실패와 관계없이 기존 backend 실행 환경 복원 및 피드백 ZIP 생성.

이미 관측한 총 166문항을 다시 평가하므로 새로운 블라인드 성능이라고
부르지 않는다. 화면 top_k=10은 고정된 제품 기본값이며 최적값 탐색이 아니다.
`passed_observed_tests`와 `passed_api_smoke`를 확인한 뒤에만 이번 실행의
성능 및 실제 검색 적용 검증 결과를 설명한다.

원본 질의 CSV·정답·검토 자료는 현재 환경의 파일을 그대로 사용한다.
피드백 ZIP에는 개인 평가 자료가 있으므로 공개 저장소에 올리지 않는다.
실행 마지막의 **Send this file:**에 찍힌 정확한 ZIP을 전달하면 된다.
같은 파일명을 교체하지 않고 매번 새 ZIP을 생성해 파일 잠금 문제를 피한다.
긴 콘솔 로그는 그 ZIP에 함께 포함된다.

분석 서비스 오류 등으로 중단한 뒤 같은 소스·설정·입력·코퍼스를 유지하는
경우에만 아래처럼 같은 결과 폴더를 이어서 실행할 수 있다.

```powershell
.\experiments\namuwiki\run_context_media_scope_fix.ps1 -Mode All `
    -OutputDir 'artifacts/실제로_생성된_결과_폴더명' -Resume
```

새 코드가 적용되거나 조건이 달라졌다면 새 결과 폴더에서 시작한다.
원래 Gemini 키·공용 MongoDB 설정은 기존 `.env`에 유지한다.
