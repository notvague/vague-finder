**포스터 수치와 시연 구성의 차이.** 코드 기본값으로 띄운 서비스는 작품명 OFF·소리 ON·D OFF다. 포스터의 개발 비교 기준(v75 A, Hit@10 121/176)은
**작품명 ON**이고, 평가기 조건(고정 분석 캐시·예열·요청 60초/질의 120초·후보 30에서 top-10 평가)에서 잰 값이다. 서비스는 화면 기준 15곡을 보여 주고
운영 예산(분석 20초·리랭킹 30초)을 쓴다. 시연 화면의 결과를 포스터 수치의 사례로 붙이지 않는다. 점검을 이유로 기본 OFF 기능을 켜지 않는다.

### 1-2. 피드백 수집이 켜져 있을 때 — 먼저 결정할 것

2026-10-20 확인 당시 메인 체크아웃 `.env`는 `FEEDBACK_COLLECTION_ENABLED=1`이었다(실행 중 프로세스 상태는 미확인).

- 켜져 있으면 **시연 검색마다 질의 원문·분석·보여준 곡이 Mongo 피드백 저장소에 기록**되고(`feedback/capture.py`), 결과 행에 "정답" 버튼이 붙는다.
  관객이 질의를 입력한다면 그 문장이 저장된다. 켤지 끌지는 시연 전에 정한다(사용자 결정).
- **모의 장애 서버도 `.env`를 읽는다.** 검색 라우트가 `src/vector_db/settings.py`(`load_dotenv()`)를 불러오므로, 메인 체크아웃에서
  `demo_faults`/`check_demo_faults`를 그대로 돌리면 모의 검색 결과가 실제 피드백 저장소에 기록될 수 있다(코드 읽기로 확인, 실행 확인은 안 함).
  모의 서버는 항상 `FEEDBACK_COLLECTION_ENABLED=0`을 명시해 띄운다. `load_dotenv()`는 이미 있는 환경변수를 덮지 않는다.
- **이미 떠 있는 모의 서버를 재사용할 때는 검사 명령의 환경변수가 그 서버에 적용되지 않는다.** `check_demo_faults`는 `--url`의 `/__fault`가 응답하면 기존 서버를 사용한다. 서버 자체가 수집 OFF로 시작됐다는 기록을 확인한 뒤 검색을 보낸다. 확인할 수 없다면 진행하지 않고, 본인이 관리하는 모의 서버만 종료·재기동한다. 다른 세션의 서버는 건드리지 않는다. 모의 `/health`에는 피드백 상태가 없으며, `--start`만 붙여도 기존 서버의 설정이 바뀌는 것은 아니다.

#### A3. `/health` 준비 판정 `[모델 0]` · 상태: 미실행

`/health`의 `status`는 예열 중에도 늘 `ok`다. **`status=ok`만으로 준비 완료라고 판정하지 않는다.** 아래 네 칸을 각각 본다.

| 칸 | 준비 완료 | 시연 전 조치가 필요한 값 |
|---|---|---|
| `warmup.state` | `ready`. `stages`에 `failed:`가 없다. Gemini 리랭커면 `reranker`가 `skipped:`인 것은 정상 | `running`·`not_started`(첫 검색이 느리다) · `partial_failure`(어느 단계인지 `stages`에서 본다) · `failed` · `stopped`. `skipped`는 `SEARCH_WARMUP=0` |
| `context.state` | `CONTEXT_WEIGHT>0`이면 `verified`(+`checked_at`). 끈 구성이면 `disabled` | `unavailable`(기동 때 확인 불가 — 배경 사실 시연 불가로 본다). `config_error`면 서버가 아예 뜨지 않는다 |
| `lyrics_cache.state` | `fresh`, `documents`가 준비한 가사 스냅샷의 예상 건수와 일치, `last_refresh_error` 없음. 가사 없는 곡이 있을 수 있어 전체 색인 5,143곡과 같아야 하는 것은 아님 | `not_created`(예열 전·예열 끔) · `empty` · `stale`이면서 `refresh_failures` 증가. `no_cache`는 TTL을 꺼둔 구성인지 별도 확인 |
| `feedback` | §1-2에서 정한 값과 같다(`collection.enabled`, `collection.ready`, `index_worker.enabled`, `retrieval.enabled`) | 정한 것과 다름 |

- 조작: 예열이 끝날 때까지 기다린 뒤 한 번 받아 저장한다.
- 실패 판정: 위 표의 오른쪽 값 → 원인을 확인하기 전까지 **차단**. 단 `stale`은 TTL이 지난 정상 상태일 수 있다(기존 판으로 검색하고 뒤에서 갱신) — `refresh_failures`가 늘 때만 차단.
- 증거: `/health` JSON(공개 전에 `context.publication`의 컬렉션 이름 정도만 남는지 확인).

### B. 첫 요청과 예열 후 요청 `[Vertex]`

#### B1. 예열 전 첫 요청 · 상태: 미실행

시연에서 예열 전에 검색할 일이 없게 하는 것이 목적이다. 필요할 때만 잰다.

- 준비: A2 직후, `warmup.state`가 `running`일 때.
- 조작: 브라우저에서 질의 1건. DevTools Network에서 `/api/v1/search` 요청의 전체 시간을 본다.
- 기대: 결과가 나온다(느릴 수 있다). 예열 중에도 검색은 된다.
- 실패 판정: 500·결과 없음·화면 멈춤 → **차단**. 단지 느린 것 → 개선(시연 절차에서 예열 완료를 기다리게 한다).
- 증거: 요청 시간·상태 코드·`X-Request-Id`, 그때의 `warmup.stages`.

#### B2. 예열 후 요청 — 발표 순서 리허설 · 상태: 미실행

- 준비: A3 통과. Vertex 호출 승인. 호출 규모: 첫 검색마다 질의 분석 1회(실패 시 최대 3회 시도), 리랭킹은 정책 생략이면 0회·아니면 묶음마다 재시도 포함 여러 회.
  재질문 검색은 기존 분석을 다시 보내므로 분석을 부르지 않는다. 실제 리랭킹 호출 수는 응답의 `explain.rerank_model_calls`로 센다.
- 조작:
  ```bash
  venv/bin/python -m src.backend.demo_rehearsal            # --url 기본 http://127.0.0.1:8000, --timeout 기본 60
  ```
  텍스트(분위기) → 이미지(표지) → 가사 → 재질문(거절 → 질문 조회 → 첫 선택지로 답) 순으로 한 번씩 보낸다. 요청 모양은 화면과 같다(`top_k` 15, `candidate_k` 30, `defer_clarify`).
- 기대: 단계마다 HTTP 200, 결과 있음, 짚을 것 0건(분석 폴백·죽은 경로·리랭킹 실패 없음), 재질문 뒤 거절 곡 미재등장·턴 +1. 종료 코드 0.
- 실패 판정: 종료 코드 2(서버에 닿지 못함) → **차단**. 분석 폴백·리랭킹 실패·죽은 경로 → **차단**(권한·쿼터·연결부터 확인). "거절한 곡이 다시 나왔다"·"턴이 하나 가지 않았다" → **차단**.
  "1위 곡에 … 경로 기여가 없다"는 실행마다 달라질 수 있는 값이다 → 원인 확인 뒤 개선으로 분류할 수 있다(순위를 합격 기준으로 삼지 않는다). "질문이 나오지 않았다"도 같다.
- 증거: 리허설 출력 전문, 서버 구간 기록(`SEARCH_TIMING_LOG`, 요청은 `X-Request-Id`로 맞춘다).

#### B3. 시간 기록 규칙 — 모든 `[Vertex]` 점검에 적용

- 기록할 것: **요청 하나의 HTTP 전체 응답 시간**(브라우저 Network 또는 리허설의 초), HTTP 상태, 결과 수, 실행 기록 줄(`runNote`)의 단계 이름, 폴백 여부(분석 폴백·리랭킹 실패/일부 적용·죽은 경로).
- 첫 요청과 예열 후 요청을 같은 표에 섞지 않는다. 질의마다 처음 쓰는 경로가 있으면 그것도 적는다.
- 평가기의 `rerank_only_ms`·리랭킹 단계 시간과 섞지 않는다. 서버 구간 기록의 `rerank`는 HTTP 전체의 일부다.
- 몇 건의 시연 요청으로 p95·중앙값·성공률을 쓰지 않는다. 표에는 "요청 n건의 개별 값"으로만 남긴다.

### D. 재질문과 거절

자동 시험이 상태 전이를 덮는다(§2). 여기서는 **실서버 + 실제 브라우저**로 한 번 이어서 밟는다 `[Vertex]`. 같은 흐름의 모의 서버 확인은 §E6·E9a·E9b `[모델 0]`이다.

화면의 한도(코드 값): 한 번에 15곡, 누적 거절 30곡 → **거절은 두 번까지**. 재질문 턴 2, 물어본 슬롯 3. 질문 조회 제한 8초, 검색 제한 60초.

#### D1. "이 중에는 없어요" · 상태: 미실행

- 준비: C0의 분위기·표지·가사 질의 중 하나로 검색.
- 조작: "이 중에는 없어요"를 한 번 누른다.

#### D3. 출생 연도 입력 · 상태: 미실행

- 준비: P7(`clearBirthYear()`). C0 출생 연도 사례.
- 조작: (a) 결과와 함께 뜬 연도 휠을 돌려 "이 연도로 찾기". 새로 고침 뒤 같은 질의를 다시 검색. (b) 다른 검색에서 "잘 모르겠어요" 또는 "그냥 결과 볼게요".
- 기대: (a) 같은 질의를 기존 분석으로 다시 찾는다 — 분석 재호출 없음, 거절 없음, 턴 그대로. 다음 검색부터는 묻지 않는다(브라우저에 저장, 서버는 저장하지 않는다). 재검색이 실패하면 앞의 결과가 그대로 남고 경고가 뜬다.
  (b) 이 검색에서는 다시 묻지 않고, 그 뒤 "이 중에는 없어요"는 성별·장르 질문 조회로 간다.
- 실패 판정: 답한 뒤에도 같은 브라우저에서 계속 물음, 답 뒤 거절이 쌓임 → **차단**. 질문이 아예 안 뜸 → 분석 결과 탓일 수 있다. 사례를 바꾸고 기록한다.
- 정리: 끝나면 `clearBirthYear()`로 지운다(다음 시연자에게 남지 않게).
- 증거: 휠 화면, 답 전후 결과의 시기, 요청 본문의 `birth_year` 유무(Network).

#### D4. 거절 한도 · 상태: 미실행

- 조작: 질문이 뜨면 "잘 모르겠어요"로 넘기며 "이 중에는 없어요"를 계속 누른다.
- 기대: 거절 두 번 뒤 거절 버튼이 사라지고 "여기까지 찾아봤어요. …"가 뜬다. 마지막 결과는 화면에 남고 눌리지 않는 버튼이 없다. 422 오류가 나지 않는다.
- 실패 판정: 세 번째 거절이 나감, 422, 마지막 결과가 사라짐 → **차단**.
- 증거: 끝 화면 스크린샷, 검색 요청 수(첫 검색 + 거절 2).

#### D5. 새 질의 시작 · 상태: 미실행

- 조작: (a) 재질문 도중 검색창에 새 질의를 넣고 Enter. (b) 검색창의 × 버튼. (c) 질문 화면이 아닐 때 Esc.
- 기대: (a) 턴 1, 거절 없음, 앞 대화의 질문·안내·펼친 근거가 남지 않는다. 앞 요청의 늦은 응답이 새 결과를 덮지 않는다. (b)(c) 결과·강조·상태줄이 지워진다.
- 실패 판정: 앞 대화의 거절 목록·질문·`known_slots`가 새 검색에 실림 → **차단**(요청 본문으로 확인).
- 증거: 새 검색의 요청 본문에서 `rejected_ids`·`turn`·`prior_analysis` 유무.

#### D6. 거절 곡 재등장 · 상태 누출 · 중복 요청 — D1~D5 동안 함께 본다

- 거절한 곡 ID가 이후 결과에 없다(같은 대화 안).
- 요청 본문의 `rejected_ids`는 본 순서대로 중복 없이 쌓인다.
- 버튼을 빠르게 두 번 눌러도 검색·조회 요청은 한 번이다.
- 다른 질의로 새로 시작하면 앞 대화의 상태가 요청에 섞이지 않는다.
- 서버 쪽 요청 간 상태 누출은 v64(모델 0)에서 12/12 사례 없음으로 확인됐다. 이번 점검은 화면 쪽만 본다. 동시 요청은 이 점검의 범위가 아니다.

### F. 브라우저 사용성

`[모델 0]`이면 모의 서버(8010)로, 실제 근거·재생 화면은 실서버(8000) `[Vertex]`로 본다.

#### F1. 발표 화면 크기 · 상태: 미실행

- 코드상 배치 경계: 1400px보다 좁으면 지도를 축소하지 않고 가로로 스크롤한다. 900px 이하에서는 레일이 위로 눕는다. 700px 이하 별도 배치가 있다.
- 조작: 발표 장비 해상도(또는 같은 창 크기)에서 지도·결과 목록·근거 패널·재질문 화면을 차례로 띄운다. 레일 접기(버튼 또는 ⌘\ / Ctrl+\)를 한 번 써 본다.
- 기대: 검색창·상태줄·결과 목록·재질문 버튼이 화면 안에 있다. 근거·점수 상세를 펼치면 레일이 늘고 지도가 따라 내려간다(좁은 화면). 제목이 겹쳐 읽을 수 없는 배율이 아니다.
- 실패 판정: 재질문 버튼이나 검색창이 화면 밖으로 밀려 조작할 수 없음 → **차단**. 가로 스크롤·여백 → 개선.
- 증거: 해상도·창 크기를 적은 스크린샷.

#### F2. 입력·스크롤·근거 펼치기·지도 조작 · 상태: 미실행

- 조작: 한글 질의를 입력하고 Enter → 결과 목록 끝까지 스크롤 → 근거 펼치기/닫기 → 점수 상세 펼치기 → 결과 행 클릭(지도 카드) → sound/mood/list 탭 전환 → 지도 스크롤.
- 기대: 새 결과는 1위부터 보인다. 근거를 닫았다 열면 점수 상세는 접힌 상태로 돌아간다. 행 클릭은 지도 보기로 바꾸고 그 곡으로 스크롤한 뒤 카드를 연다. sound/mood 탭을 바꾸면 열린 카드와 재생 중인 영상이 닫히고 검색 강조는 남는다.
- **한글 입력 Enter:** 검색창의 Enter 처리는 조합 중 여부(`isComposing`)를 보지 않는다(코드 읽기). 마지막 글자 누락이나 검색이 두 번 나가는지 Network로 본다 — 실제 동작은 미확인.
- 실패 판정: 결과·근거를 볼 수 없음, 같은 질의가 두 번 나가 결과가 바뀜 → **차단**. 같은 질의가 두 번 나가지만 마지막 결과가 정상 → 개선(Vertex 호출이 두 배).
- 증거: 요청 수, 이상이 있으면 화면 녹화.

#### F3. YouTube 재생과 재생 불가 · 상태: 미실행

- 코드상 동작: 재생은 곡 카드의 ▶ 버튼이 `youtube-nocookie.com/embed/<id>?autoplay=1` iframe을 연다. 2026-10-20 `map_data.json` 기준 5,143곡 모두 영상 ID가 있어 ▶ 버튼이 늘 보인다.
  임베드가 막힌 영상(소유자 차단·지역 제한·삭제)은 iframe 안에 YouTube 오류가 뜰 뿐 **화면 코드는 실패를 알지 못한다.**
- 조작: (a) 결과 곡 하나 재생 → 다른 곡 카드 열기 → 다시 재생 → ▶로 멈춤. (b) 재생이 안 되는 곡을 만나면 카드를 닫고 새 검색·근거 펼치기·재질문을 이어서 한다. 네트워크를 끄는 방식으로 재생 실패를 만든 경우에는 먼저 네트워크를 복구한 뒤 새 검색·재질문을 확인한다. 네트워크 단절 중 HTTP 실패를 재생 오류의 영향으로 판정하지 않는다.
- 기대: 다른 곡 카드를 열면 앞 영상이 닫힌다. 재생 실패 뒤에도 검색·근거·재질문이 그대로 동작한다. 재생한 곡은 "들음" 표시가 남는다(`vf.heard`).
- 실패 판정: 재생 실패 뒤 검색 화면을 쓸 수 없음 → **차단**. 시연 곡이 임베드 차단 → 그 곡을 시연에서 빼고 기록(개선: 화면이 재생 불가를 알리지 못함).
- 증거: 재생한 곡 ID와 결과(재생됨/임베드 오류/네트워크 실패).

#### F4. 표지·네트워크 · 상태: 미실행

- 표지는 응답의 `cover_url` 또는 지도 데이터의 멜론 CDN 주소를 브라우저가 직접 불러온다. 주소가 없거나 못 불러오면 회색 사각형이다.
- 시연 장소에서 표지가 안 뜨면 검색 동작은 그대로지만 표지 사례(C0)의 설득력이 떨어진다 → 표지 사례만 빼고 기록. 차단 여부는 시연 범위를 정할 때 결정한다.

## 5. 실행 전에 정할 것 · 아직 모르는 것

**사용자가 정할 것.**

1. 포스터에 실제 화면을 싣는지, 현장 시연을 하는지(하지 않으면 이 점검표는 실행하지 않는다).
2. 시연 중 피드백 수집을 켤지(§1-2).
3. 실서버 점검(§3-B·C·D)의 Vertex 호출 범위·예산 승인.
4. 시연 질의 최종 목록(C0에서 고르거나 새로 정한다). 관객 입력을 받을지.
5. 시연 서버의 Qdrant 방식(로컬 파일 / 서버)과 체크아웃.

**아직 모르는 것(이 문서 작성 시점).**

- 현재 코드에서 브라우저 장애 화면 11항목의 결과(마지막 실측은 2026-10-01 옛 화면).
- 현재 기본 구성(5,143곡·Gemini listwise·희소 사실 검증 끔·Context 0.5)의 리허설 시간.
- 배경 사실 사례(t042·t071)가 현재 코드에서 근거(`context_evidence`)를 보이는지.
- 출생 연도 사례가 실제 분석에서 질문을 띄우는지.
- 시연 장비의 해상도·네트워크에서의 표지·재생.
- 한글 입력 Enter 동작, 취소한 검색의 서버 쪽 처리 여부.
- 분석까지 실제 모델일 때 장애 요청의 HTTP 전체 상한(계산값 약 52초, 미측정).
- 동시 요청(관객이 여러 기기로 접속하는 경우). 이 점검표의 범위가 아니다 — 데이터 정책 §4대로 팀이 운영하는 환경 한 곳에서 시연한다.
