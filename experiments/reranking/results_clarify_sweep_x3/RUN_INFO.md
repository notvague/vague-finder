# 답변 보너스 배수 스윕 (×3 / ×5 / ×8)

`clarify.ANSWER_MATCH_MULTIPLIER`를 정하기 위한 보정 측정.
`sweep_x3` · `sweep_x5` · `sweep_x8` 세 디렉터리가 한 세트이며, 이 문서가 셋을 대표한다.
×1.5 데이터는 `../results_clarify_v04/`에 있다(당시 기본값).

## 왜 쟀나

답변 반영을 재검색에서 재정렬로 바꾸자 오답 시 후보 이탈이 0이 됐지만,
dev 회수가 8/9 → 6/9로 떨어졌다. 잃은 c701·c705는 둘 다 사용자가 성별을 잘못
기억해 후보 풀이 통째로 반대쪽으로 채워진 질의로, 정답이 21위·17위에 있었다.
재검색 시절에는 기존 성별 부스팅의 **불일치 페널티**까지 작동해 정답이
올라왔지만, 재정렬은 보너스만 주므로 세 칸 오르는 데 그쳤다.

크기 문제인지 방식 문제인지 가리기 위해 배수를 키워 가며 쟀다.

## 실행

```bash
venv/bin/python -m src.retrieval.evaluate_clarification --split dev \
  --query-ids c607,c701,c705,c707,m402,q101,q115,q203,q316 \
  --answer-multiplier {3,5,8} \
  --output-dir experiments/reranking/results_clarify_sweep_x{3,5,8}
```

개입 9건만 돌렸다. 나머지 44건은 답변이 없어 이 코드 경로를 타지 않는다
(전체 실행에서 53/53 동일함을 `v05`·`v06`에서 확인).

## 결과 (dev 개입 9건)

| 정책 | ×1.5 | ×3 | ×5 | ×8 |
|---|---|---|---|---|
| reject_only | 3/9 | 3/9 | 3/9 | 3/9 |
| **rule:oracle** | 6/9 | **8/9** | 8/9 | 8/9 |
| oracle:vocal_gender | 5/9 | 7/9 | 7/9 | 7/9 |
| rule:noisy | 1/9 | 1/9 | 1/9 | 1/9 |
| 오답 시 후보유지 | 0.889 | 0.889 | 0.889 | 0.889 |

**×3에서 포화한다.** 크기 문제였고 방식 문제는 아니었다.

×8까지 키워도 `noisy:*`가 나빠지지 않았다. 후보 풀이 고정이라 보너스가 아무리
커도 정답을 풀에서 밀어낼 수 없기 때문이다.

## 선택 — ×3

같은 성능이면 작은 값을 택했다.

- 보너스가 작을수록 기존 검색·리랭킹 신호를 덜 덮어쓴다. 평가 세트에 없는
  케이스에서 과하게 개입할 위험이 줄어든다.
- 기존 명시 부스팅 체계(0.25~5, 제목 일치가 최대 ×5) 안에 자연스럽게 들어간다.
  사용자 답변이 제목 일치보다 강한 신호는 아니다.
- 표본 9건에서 ×3과 ×5를 가르는 근거가 없으므로 큰 값을 택할 이유가 없다.

전체 dev 확인은 `../results_clarify_v06/`.

> ⚠️ 이 스윕의 detail CSV에서 type·release_era 정책은 무효다(당시 미구현으로 reject_only와 동일). 배수 선택 근거인 `rule:oracle`·`vocal_gender`·`noisy:*`(성별·장르)는 규칙이 두 슬롯만 쓰므로 유효하다.
