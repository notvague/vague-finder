- 순서 차이의 원인(질의마다, 이 순서로 판정): failure_fallback(한쪽이라도 실패·부분·예산 소진) → policy_skip_order(양쪽 정책 생략, 모델 없이 후보 순서 차이) → input_change(후보 집합/순서/점수·가사·보호·그룹 입력·첫 프롬프트 중 하나가 다름) → model_variation(입력이 같은데 모델 출력이 다름).

### 5-3. 판단 분류(새 허용 손실선·통과 기준을 만들지 않는다)

- **차이 없음**: 두 전후 쌍에서 정답 위치가 바뀐 질의가 없거나, 바뀐 질의가 모두 같은 구성 반복에서도 바뀌는(모델 변동) 질의다.
- **관측된 개선 / 관측된 악화**: 두 전후 쌍에서 **같은 방향**으로 바뀐 질의가 있고, 그 질의가 입력 변화 질의이며, 같은 구성 반복에서는 바뀌지 않았다. 질의 수와 방향을 그대로 적는다. 반복이 2회뿐이라 인과는 확정하지 않는다.
- **변동·장애로 판단 불가**: 비교 질의에 실패·예산 소진이 섞이거나, 반복 변동이 전후 차이를 가릴 만큼 크다.
- 악화가 보이면 원인을 진단하고, 옛 비결정적 정렬로 되돌리지 않는다. 개선·동률도 통계적 우월성·비열등성 증명으로 쓰지 않는다.

### 5-4. 수정 후 서버 기준선으로 쓸 조건(결과 전 확정, 품질 수치 기준 없음)

후1·후2가 모두 완료(176건, 실패 포함 집계 가능)되고, 두 실행의 입력이 직전·직후 오프라인 지문과 같으며, 서버 상태가 기준과 같고, 실패·예산 소진 수가 보고되어 있으면 "수정 후 서버 기준선"으로 기록한다. 품질 숫자로 합격·불합격을 정하지 않는다. 실패가 섞이면 그 사실을 기준선과 함께 적는다.

### 5-5. 호출·비용 보고

### 5-6. 평가기와 서비스의 차이(명시)

평가기는 top_k 30, HTTP 서비스는 top_k 15다. 서비스는 보호 tier가 결과 자리를 채우면 남은 묶음을 부르지 않는다. dev 176에서 평가기 리랭커 호출 163 · 서비스 161이고, **n064는 평가기 3그룹 · 서비스 1그룹**이다(v65 §5-4). 첫 그룹 입력은 같다. 그래서 이 측정은 서비스 응답의 품질이 아니라 평가기 기준선이다. v65의 실제 HTTP 오프라인 검증(같은 백엔드의 평가기 ↔ HTTP 후보 176/176)이 둘을 잇는 근거다.

## 10. 미검증·한계

1. **실제 HTTP 서비스 경로(top_k 15)의 모델 포함 품질**은 재지 않았다. n064처럼 그룹 수가 다른 질의는 서비스 결과가 평가기와 다를 수 있다.
2. 수정 전 결과는 이 서버 적재 상태 하나다. 다른 적재·재시작 상태의 수정 전 품질, 동점 처리의 평균 효과는 모른다.
3. 모델 변동: 이번 1시간 안에서는 0이었지만, v63(같은 날 새벽)과 t026에서 같은 입력에 다른 응답이 나왔다. 다른 시간대의 반복 변동 크기는 이 측정으로 말할 수 없다.
4. 로컬 모드 실제 평가(이번 범위 밖), n071/q205 정밀도 차이의 품질 영향(로컬 미측정), c707 같은 sparse 점수 정밀도 차이의 빈도.
5. 동시 적재·배포 하드웨어·실제 Mongo 가사 경로(스냅샷만 사용).
6. 피드백 사례 검색(기본 꺼짐)은 이번 실행에서 쓰이지 않았다.
7. D 활성화·서버 배포 준비는 이 결과로 끝나지 않는다.
