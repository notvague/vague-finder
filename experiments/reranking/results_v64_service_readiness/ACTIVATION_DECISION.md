# 속성 조건 보조 경로(D) 활성화 판단서 (2026-10-17, v64)

**결론: 증거 부족 — 지금은 OFF(`ATTR_FILTER_WEIGHT=0`, 현행 기본값)를 유지한다.**
운영 안전성(경로 여닫기·장애 처리·상태·지연)에는 켜는 것을 막는 결함이 없다. 다만 **품질 이득을 보인 근거가 정책을 고른 dev 세트 안의 결과뿐**이다.
독립 세트(v10 test 42)에서는 이득도 손실도 0이었다. 이번에 D에서만 생기는 2턴 손실 경로도 하나 새로 확인했다(§1-④).
켤지는 사용자 결정이다. 켠다면 §3의 설정·확인·복귀 절차를 따른다.

## 2. 왜 "조건부 활성화"가 아니라 "증거 부족"인가

- 켜는 근거는 ①인데, ①은 정책을 고른 표본 안의 결과다. 독립 확인 ②는 0이다. "켜면 사용자가 더 잘 찾는다"는 주장을 지금 자료로는 할 수 없다.
- 끄는 근거(손실)도 독립 자료에서는 0이다. 확인된 위험은 사례 단위다: 폴백 시 밀림(t014), 성별 답 뒤 장르 제외(q112). 그래서 "OFF 유지 권고"라고 단정할 근거도 없다.
- 지연·장애 처리에는 차단 요인이 없다. 결정을 가르는 것은 품질 근거다.

### 판단을 바꿀 증거 (새로 모아야 하는 것 — 이번 dev·test로 재튜닝하지 않는다)

1. **새 독립 질의 세트**(dev·v10 test와 겹치지 않음)에서 A/D 각 2회 이상. 보조 경로가 열리는 질의(시기 창 + 성별/장르/형태)가 충분히 들어 있어야 한다. 사전 기준 예: D Hit@10 ≥ A, 손실 질의 사유 기록.
2. 같은 자료로 **2턴 흐름**(성별 답 포함)을 돌린다. ④의 q112형 손실이 얼마나 자주 생기는지 본다.
3. 운영 Vertex **실패율**(일정 기간 `reorder_stage=model_failed` 비율). D의 폴백 손실 기대값 = 실패율 × "후보 순위가 D에서 내려가는 질의" 비율.
4. (선택) conditional 변형 — "1턴에 장르로 연 필터는 성별 답이 와도 장르를 유지" — 을 위 새 자료에서 별도 A/B.

## 3. 켤 때 (사용자가 켜기로 결정한 경우의 정확한 절차)

### 3-1. 설정

운영 `.env`에 두 줄만 바꾼다(나머지는 코드 기본값과 같지만, 오타 방지를 위해 명시를 권한다).

```
ATTR_FILTER_WEIGHT=0.5
ATTR_FILTER_GENRE_POLICY=conditional
ATTR_FILTER_GATE=era_plus
ATTR_FILTER_K=30
ATTR_FILTER_USE_GENRE=1
```

- **주의 — 잘못된 값은 조용히 기본값이 된다**: `GENRE_POLICY` 오타는 `always`, `GATE` 오타는 `era_plus`, `K` 오류는 30이다(`search_router._attr_filter_*`).
  응답 explain에는 정책 판정이 없다(v56 ④·v64 §7-④). 그래서 켠 뒤 아래 3-2로 실제 값을 확인해야 한다.
- 함께 두는 값(이번 검증 조건): `CONTEXT_WEIGHT=0.5` · 리랭커 기본(요청 20초 · 공유 예산 30초 · 재시도 3) · 후보 30 · 화면 top_k 15.

### 3-2. 켠 직후 확인 (모델 호출 없이 가능한 것부터)

1. 서버 재기동 → `/health`: `context=verified`, `warmup=ready`. 프로세스 환경에서 위 5개 값을 확인한다(로그 또는 `GeminiListwiseRerankerConfig`와 함께 기록하는 점검 스크립트).
2. 고정 질의 확인(이번 v64 표본 재사용 가능 — `latency_sample.json`):
   - 닫힌 질의(c601 등)는 끄기 전과 후보 지문이 같아야 한다.
   - 열린 질의(m103·q101 등)는 `SEARCH_TIMING_LOG`에 `path.attr_filter` 구간이 있어야 한다.
   - 합성 0곡은 경로가 열리고 후보 30이 유지되어야 한다.
3. 지연 관측: 열린 질의의 검색 단계 증가가 이번 실측 범위(질의 단위 +24~+141ms, 로컬 Docker)와 크게 다르면 원인을 본다. 이 범위는 관측값이지 합격선이 아니다.
4. 첫 운영 기간 관측: `reorder_stage` 분포(특히 `model_failed`·`model_partial`·`budget_exhausted`), 열린 질의 비율, 2턴에서 성별 답 뒤 후보 변화.
5. 서버 모드로 배포한다면 `SERVER_LOADING_PLAN.md`와 v64 §7-①(로컬↔서버 동점 순서 차이)을 먼저 본다. 로컬 기준선 숫자가 서버에서 그대로 재현되지 않는다.

### 3-3. OFF 복귀

1. `.env`의 `ATTR_FILTER_WEIGHT=0`(다른 네 줄은 그대로 둬도 효과 없음 — 가중 0이면 필터를 만들지 않는다).
2. 서버 재기동(환경변수는 기동 때 읽는다).
3. 확인: 열린 질의(m103 등)에 `path.attr_filter` 구간이 없어야 한다. 후보 지문이 OFF 기준(이번 v64 A의 `sweep_per_query.csv`, 서버 모드)과 같아야 한다.
4. 색인·DB·캐시는 바꿀 것이 없다. 보조 경로는 질의 시점 필터일 뿐 저장 자료를 만들지 않는다.
