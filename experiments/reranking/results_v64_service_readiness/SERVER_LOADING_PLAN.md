# 서버 모드 Qdrant 적재 운영안 — 검색 중단 절차(초기 배포 권고) · 불변 세대 발행(무중단 후속 설계)

작성 2026-10-17(v64). **설계·운영안이며 구현·실행하지 않았다.** 운영 컬렉션·별칭·배포 구성은 바꾸지 않았다.
근거 코드는 `dd5cc3e` 기준이다.

## 0. 왜 필요한가 — 현재 코드의 전제

- 하이브리드 조회는 한 요청 안에서 **count → dense → sparse → payload** 네 번 Qdrant를 부른다(`QdrantIndex.query`, v62).
  네 호출 사이에 컬렉션이 바뀌면 count와 조회 대상이 어긋난다. 새 판이 더 크면 전수 합산이 다시 잘리고(v61 결함 재발),
  payload 조회에서 곡이 빠질 수 있다. 반환 건수로는 감지할 수 없다(v61 §8).
- 한 요청은 곡 텍스트·이미지·오디오·Context dense/sparse 컬렉션을 **경로마다 따로** 읽고, 그 뒤 곡 메타데이터를 텍스트 컬렉션에서 다시 읽는다(`fetch`).
  Context 후보도 곡 컬렉션 payload로 메타데이터를 채운다.
- **별칭을 한 번에 바꾸는 것만으로는 한 요청의 일관성이 생기지 않는다.** Qdrant는 별칭을 호출마다 푼다.
  교체가 원자적이어도, 교체 전에 시작한 요청의 count는 옛 판에서, 뒤 호출은 새 판에서 읽을 수 있다.
  Context는 이미 세대 컬렉션과 별칭 2개를 원자 교체로 발행한다(`context_qdrant.publish_context_qdrant`). 검색은 `search()` 한 번에
  별칭을 한 번 풀어 물리 이름으로 dense·sparse를 읽는다(`ContextQdrantSearch._snapshot`). 하지만 곡 컬렉션과는 세대가 묶여 있지 않고,
  `--prune` 정리도 진행 중 요청을 기다리지 않는다.
- 질의 쪽 자료도 색인과 짝이 맞아야 한다. BM25 파라미터(`artifacts/bm25_params.json`)와 오디오 중심값(`audio_mean.npy`)은
  프로세스 기동 때 한 번 읽는다(singleton). 색인의 sparse·오디오 벡터를 새 파라미터로 다시 만들면, **서버를 다시 띄우기 전까지 질의 인코딩이 옛 판으로 남는다.**
- 현재 운영은 **로컬 파일 모드**다(`.env`의 `QDRANT_PATH`, `QDRANT_URL` 없음). `docker-compose.yml`에는 backend·mongodb만 있고 Qdrant 서비스가 없다.
  로컬 모드는 저장 폴더를 한 프로세스만 열 수 있다. 그래서 서버가 떠 있으면 적재기(`qdrant_load`)가 열리지 않고, 적재는 지금도 사실상
  "서버를 내리고 적재"다. 아래 절차는 **서버 모드(`QDRANT_URL`)로 옮길 때** 필요하다. 서버 모드에서는 적재기와 검색 서버가 동시에 같은 컬렉션을 만질 수 있다.

## 1. 초기 서버 배포 권고 — 적재 중 검색 중단 절차

### 1-1. 지금 코드로 가능한 차단·배출 수단

- **진입 차단·배출 = 백엔드 프로세스 정상 종료.** 앱에는 유지보수 모드·준비 게이트가 없다(`/health`는 예열 중에도 `status: ok`).
  uvicorn 정상 종료(SIGTERM)는 새 연결을 받지 않고 진행 중 요청이 끝나기를 기다린다(`--timeout-graceful-shutdown`으로 상한).
  그 뒤 lifespan 종료가 예열 정지 → 가사 갱신 정지 → 색인 작업 정지 → 검색 스레드풀 비우기(`close_vector_client`) 순으로 정리한다.
  요청 하나의 최대 시간은 분석 22초 + 검색 + 리랭킹 공유 예산 30초 + 직렬화다. 상한을 **90초 이상**으로 두면 정상 요청이 끊기지 않는다(v57로 리랭킹 단계가 30초 마감 하나를 공유한다).
- 앞단에 리버스 프록시가 있다면 `/api/v1/search`를 503(고정 안내 문구)으로 먼저 막고 배출할 수 있다. 하지만 지금 배포 구성에는 프록시가 없다. 앱 안 유지보수 스위치는 별도 구현 범위다(§3).
- **BM25·오디오 중심값이 바뀌는 적재는 어차피 백엔드를 다시 띄워야 한다**(§0). 초기 배포에서는 "내리고 적재하고 다시 띄우기"가 가장 단순하고 정확하다.

### 1-3. 실패 시

- **차단을 유지한다**(백엔드를 띄우지 않는다). 절반만 적재된 판으로 검색을 재개하지 않는다.
- 이전 판 복구: 1단계 스냅샷을 컬렉션별로 복원(또는 저장 볼륨을 되돌림)하고 이전 `bm25_params.json`·`audio_mean.npy`를 되돌린다.
  Context는 이전 세대 컬렉션이 남아 있으면 별칭만 되돌린다(`--prune`을 쓰지 않았을 때).
- 복구한 판에 5단계 검증을 다시 돌린다. 통과한 뒤에만 6 → 7.
- 실패 원인·적재 출력·검증 결과를 기록한다. 다음 시도는 복사본 대상 리허설부터 한다.

### 1-4. 이 절차가 보장하지 않는 것

- 다운타임이 있다(프로세스 재기동 + 모델 예열 + 최초 가사 적재). 이 PC 기준으로 예열은 수 초~십수 초(v64: import 3.7초, 예열 완료까지 1분 안)였지만, 가사 최초 적재는 Mongo에서 약 350초다(스냅샷 재생 0.5~0.8초는 실제 Mongo 시간이 아니다).
- Mongo 가사는 Qdrant와 별개로 바뀐다. 백엔드가 떠 있는 동안 Mongo를 고치면 TTL(300초) 갱신으로 새 가사가 들어온다. 그래서 같은 점검 시간에 둘을 함께 바꿔야 한다.
- **로컬↔서버 동점 순서 차이**(v64 §5-2): 같은 자료라도 백엔드가 바뀌면 이미지 동점 묶음(1,395곡이 다른 곡과 같은 이미지 벡터)의 순서가 달라진다. 그래서 평가 기준선(로컬)의 후보가 그대로 재현되지 않는다(dev 176 중 34건 순서, 9건 집합). 재적재 뒤에도 서버 내부 순서가 바뀔 수 있다. 결정적 동점 처리는 별도 수정이다(§3).

## 2. 무중단 대안 — 불변 세대 발행(후속 설계)

### 2-1. 원칙

1. **세대 = 한 번 쓰고 다시 쓰지 않는 물리 컬렉션 묶음.** 곡 텍스트·이미지·오디오·Context dense·Context sparse를 같은 세대 id로 만든다(`…__dev__gen_<id>`).
   발행 뒤에는 그 컬렉션에 쓰지 않는다. 고칠 일이 있으면 새 세대를 만든다.
2. **세대 manifest** 하나가 세대를 정의한다: 물리 컬렉션 이름 5개 · 점 수 · 텍스트 내용 지문 · 코퍼스 sha · BM25 파라미터 sha · 오디오 중심값 sha ·
   Context build id · 가사 판 기준(아래 2-4) · 만든 코드 sha. 서버는 manifest와 Qdrant 실제 상태가 맞을 때만 그 세대를 쓴다(v60 기동 검사를 세대 단위로 넓힌 것).
3. **요청 시작 때 세대를 한 번 고정한다.** 라우트 입구에서 "현재 세대" 포인터를 읽어 요청 객체(인자 또는 ContextVar)에 묶는다.
   그 요청의 count·dense·sparse·payload·fetch·Context 조회는 **별칭이 아니라 그 세대의 물리 컬렉션 이름**으로 부른다.
   지금 `QdrantIndex`는 인덱스 이름으로 컬렉션을 정하고 `ContextQdrantSearch`는 호출마다 별칭을 푼다. 둘 다 "요청 세대를 받는" 형태로 바꿔야 한다.
4. **질의 쪽 자료도 세대별로 쥔다.** BM25 인코더·오디오 중심값을 세대 id로 찾는다(새 세대 발행 때 미리 적재하고, 이전 세대 것은 그 세대가 정리될 때까지 유지).
   임베딩 모델(KoE5·SigLIP2·CLAP)이 바뀌는 세대는 무중단 대상에서 뺀다(재기동).

### 2-2. 발행 순서

1. 새 세대 컬렉션 생성 → 적재 → §1-2의 5단계 검증(세대 안에서) → manifest 기록.
2. 서버가 새 세대 manifest를 확인하고 BM25·중심값을 미리 올린다(아직 요청에는 안 씀).
3. **포인터 원자 교체.** 앱 안 포인터를 바꾸거나, Qdrant 별칭 하나(`vaguefinder-current__dev` → 세대 marker)를 바꾸고 서버가 요청마다 그 별칭을 **한 번만** 읽는다.
   이후 시작한 요청만 새 세대를 쓴다. 이미 시작한 요청은 끝까지 옛 세대를 쓴다.
4. 관측: 요청별 세대 id를 timing·explain·피드백 기록에 남기고, `/health`에 현재 세대·보유 세대·세대별 진행 중 요청 수를 보인다.

### 2-3. 정리·롤백

- **정리:** 세대별 진행 중 요청 수(참조 수)가 0이 되고, 그 뒤 유예 시간(요청 최대 시간의 수 배, 예: 5분)이 지나야 옛 세대를 지울 수 있다.
  **직전 세대 하나는 롤백용으로 남기고 그 이전 세대부터 지운다.** 지우기 전에 포인터·manifest가 그 세대를 가리키지 않는지 다시 확인한다(Context `_prune_inactive_generations`의 별칭 확인과 같은 원칙에, 참조 수 확인을 더한다).
- **롤백:** 직전 세대가 남아 있으면 포인터만 되돌린다(같은 원자 교체). BM25·중심값도 그 세대 것으로 돌아간다. 직전 세대가 이미 지워졌으면 §1-3(차단 + 스냅샷 복구)으로 간다.

### 2-4. 일관성 범위 — 보장하는 것과 못 하는 것

| 자료 | 세대로 묶을 수 있는가 | 비고 |
|---|---|---|
| 곡 텍스트·이미지·오디오 컬렉션 | **예**(물리 이름 고정) | count·dense·sparse·payload·fetch가 한 세대 |
| Context dense·sparse | **예** | 지금도 쌍은 일관. 곡 세대와 같은 manifest에 묶어야 곡 메타데이터와도 맞는다 |
| BM25 파라미터·오디오 중심값 | 예(세대별 적재) | 서버 메모리에 두 세대 분을 동시에 둔다 |
| Mongo 가사(`songs`) | **아니오(현재 구조)** | 다른 DB이고 프로세스 안 TTL 판으로 갱신된다. 할 수 있는 것: 세대 manifest에 "가사 판 기준(문서 수·내용 지문)"을 적고, 가사 판의 곡 id ⊆ 세대 곡 id를 검사하고, 어긋나면 가사 결과에서 세대에 없는 곡을 빼고 기록한다. 완전한 일치에는 세대 표시가 있는 가사 컬렉션이나 스냅샷 발행이 필요하다 |
| 피드백 승인 사례 컬렉션 | 별도 수명 | 곡 세대와 무관하게 TTL·승인으로 관리(`docs/feedback.md`). 세대에 없는 곡은 보충에서 제외 |
| 화면 지도(`map_data.json`) | 별도 | 정적 파일. 세대 id를 같이 적어 화면 버전을 맞춘다 |
| 분석 캐시·평가 기준선 | 해당 없음 | 평가 실행은 세대 id를 runinfo에 적는다 |

### 2-5. 구현 범위(별도 작업으로 남김)

`QdrantIndex`·`QdrantVectorClient`에 요청 세대 인자 · 라우트 입구 세대 고정과 ContextVar 전달 · `ContextQdrantSearch`의 별칭 대신 세대 이름 ·
세대 manifest 형식과 기동/발행 검사 · BM25·중심값 세대별 보관 · 참조 수와 정리 작업 · `/health` 세대 표시 · 적재 CLI의 세대 모드(`qdrant_load --generation`) ·
시험: 발행 도중 요청(교체 전 시작 요청이 끝까지 옛 세대로 읽는가), 정리 경쟁, 롤백, 세대 불일치 기동 실패.

## 3. 별도 수정 후보(이번에 구현하지 않음)

1. 앱 안 유지보수 스위치(검색 503 + 고정 안내, `/health`에 상태) — 프록시 없이 진입 차단을 하려면 필요하다.
2. 결정적 동점 처리 — 경로 결과를 (점수 내림차순, song_id) 순으로 정렬해 로컬·서버·재적재 사이 순서를 고정한다. 후보 순서가 바뀌므로 기준선 재측정과 함께 결정한다(v64 §5-2).
3. 속성 필터 대상 필드의 payload 색인(서버 모드) — D의 추가 지연 대부분이 필터 count다(v64 §5-3). 적재기 변경이며 결과 동일성 검증이 필요하다.
