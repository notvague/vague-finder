# v0.22 — 코퍼스를 3,010곡 세트로 교체한 뒤 다시 잰다 · 2026-09-30

> 곡 수만 늘린 실험이 아니다. 수집본·임베딩·색인(BM25·오디오 센터링·Mongo 가사)이 함께 바뀐
> **코퍼스 교체** 결과다. 952곡과 비교할 때는 `results_v21_ce_topn/scored20_fullnorm`을 쓴다.

**결과: 대부분의 지표가 떨어졌다 (dev Hit@10 45/57 → 36/57, test Hit@1 14/25 → 10/25.
test Hit@5만 같다).** 정답 라벨이 952곡 안에서만 붙어 있어, 이 숫자는 **불완전한 라벨에 따른
잠정 평가**다. 하락이 어디서 왔는지(후보 폭, 새 경쟁곡, 기존 곡의 검색 신호 변화, 라벨 누락)는
아직 나누어 재지 않았다.

## 관찰 1 — 정답이 최종 후보 밖으로 빠진 질의가 늘었다

dev에서 새로 빠진 질의는 9건이다: c603 · c701 · m302 · q110 · q112 · q115 · q203 · q208 · q210.
test는 v21과 같은 5건이다.

q110·q112는 v21에서 1위였다.

| | v21 기록 | v22 기록 |
|---|---|---|
| q110 | 텍스트 경로 8위 · 제목 의미 경로 1위 · 편성 경로 14위, 성별·제목 의미·그룹 형태 가산 | 최종 후보 30 밖 |
| q112 | 편성 경로 1위 · 의미 보조 경로 29위, 편성·장르·시기 가산 | 최종 후보 30 밖 |

**어느 단계에서 빠졌는지는 확인하지 못했다.** 저장된 기록은 "정답이 후보 풀에 없음"까지만
남기므로, 경로 회수·RRF 융합·가산 후 절단 중 어디서 사라졌는지 구분할 수 없다.
후보 폭이 원인이라는 것은 실험으로 확인할 **가설**이다.

실험할 때 주의: 지금 `candidate_k`는 각 경로가 가져오는 깊이와 최종 후보 수를 함께 정한다
(`src/retrieval/search_router.py` `candidates`·`pool_k`). 값만 올리면 최종 후보 수와 검색 점수
정규화 범위까지 바뀌어, v21에서 문제가 됐던 정규화 효과가 섞인다.

## 관찰 2 — 새 곡 중 질의에 맞는 곡이 있어 보인다

반환된 top-10 중 952곡에 없던 곡이 dev 329/570 · test 153/250이다.
나빠진 28건 중 27건에서 정답보다 앞에 새 곡이 왔다.

그중 일부는 질의 설명에 맞는 다른 곡으로 보인다. 아직 판정하지 않았다.

| 질의 | 무엇이 보이나 |
|---|---|
| m104 | 같은 드라마 OST로 보이는 다른 남성 보컬 곡 2곡이 정답 앞에 왔다 |
| c603 | 경연 프로그램에서 남성 가수가 다른 가수 곡을 다시 부른 것으로 보이는 곡이 앞에 왔다 |
| c605 | 배우가 주연 작품에서 직접 부른 것으로 보이는 다른 곡이 앞에 왔다 |
| m301 · m303 · q116 · m402 · q304 · q312 | 커버 색·분위기만 말한 질의라 새 곡 중 맞는 커버가 있을 수 있다 |

반대로 q110·q112·q208·q210·q202·c601·c602·c606·q109처럼 정답이 분명한 질의는 실제로 놓친 것이다.

**라벨을 보강해도 모든 지표가 오르지는 않는다.** 기존 정답을 두고 정답을 추가하면 Hit·MRR은
내려가지 않지만, Recall은 정답 수가, nDCG는 이상적 순위 점수가 분모라서 내려갈 수 있다.

## 관찰 3 — CE 20곡 채점 제한을 다시 볼 이유가 있다

정답의 후보 순위가 21~30위인 질의가 dev 5건 · test 2건이다. 이 곡들은 CE가 채점하지 않는다.
952곡에서 확인한 20곡 제한의 손익(v21)을 3,010곡에 그대로 가져올 수 없다.

## 이 숫자의 위상과 다음 순서

현행 3,010곡의 **잠정 기준선**이다 (v06 라벨 기준, 라벨 검토 전). 952곡과 비교할 때는 v21을 쓴다.

라벨 검토는 v06의 모호한 질의(`docs/eval/queries.json`의 `tier`가 `vague`인 72건)를 대상으로 한다.
기존 타깃(`positives`)은 그대로 두고, 팀이 합의한 허용 정답을 별도로 더한다(기획의 이중 정답 구조).
검토표와 근거 자료는 곡 목록 공개 방침에 따라 레포 밖(`data/`, git 제외)에 둔다.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 라벨 판단 기준을 정하고 검토 | "찾으려던 원래 곡"과 "단서에 맞는 허용 정답"을 구분한다. 나빠진 28건에서 시작하되 모호한 질의 전체에 같은 기준을 적용한다 |
| 2 | 새 라벨 버전으로 지표 재계산 | v06 라벨과 이 폴더는 보존한다. 라벨만 바뀌면 검색을 다시 돌리지 않고 저장된 top-10으로 계산한다 |
| 3 | 후보 탈락 단계 확인·깊이 실험 | 경로 회수 → 융합 → 가산 → 최종 후보에서 정답 위치를 기록한다. 경로 깊이만 넓히고 최종 후보 30·CE 20은 유지한다 |
| 4 | 3,010곡에서 CE 20곡 제한 재검증 | 같은 후보를 놓고 20곡·30곡 채점을 비교한다 |
| 5 | 채택 조건으로 API 지연·데모 확인 | 예열 후 요청 전체 중앙값·p95, 재질문 동작 |
