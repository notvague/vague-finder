## 2. Context 끄기 = 무엇을 끄는가 (코드 확인)

`CONTEXT_WEIGHT=0`이면 `SearchRouter.search`의 `use_context_path`가 거짓이 되어(`search_router.py` 1321~1327행) **Context Qdrant 조회 자체를 하지 않는다.** 그 결과
(1) RRF 네 번째 목록이 비고 가중 0, (2) Context 히트가 있을 때만 쓰는 "융합 절단 없음"(`top_k=None if context_hits`) 분기도 타지 않으며, (3) `context_hits_out`이 비어 응답 근거도 없다.
가중치만 0이고 조회는 하는 상태가 아니다. 반대로 "후보 보충"에 해당하는 것은 (2)뿐이며 별도 스위치가 없다 — 그래서 A/B는 정확히 "Context 경로 유무"다.
**평가기(`evaluate_search_accuracy`)의 리랭커는 A·B 어느 쪽도 나무위키 사실을 받지 않는다**(후보 `MatchingTrack`만 전달, 프롬프트의 `relation_context_tags`는 Text payload). 서비스 경로도 Context 근거는 리랭킹 뒤 결과에 인용으로만 붙인다(`routes/search.py`). 따라서 B의 리랭킹 차이는 전부 **후보 집합의 차이**에서 온다.

실행 기록으로 확인: A의 explain 176건에는 `context` 경로 기여가 0건, B에는 11개 질의 14곡에 있다(정답에 붙은 것은 q203 Context 2위 · t042 1위 · t071 1위). 후보 집합 지문(`candidate_digest`)은 176건 중 18건에서 A≠B.

### 4-4. 가장 큰 실패 원인

1. **후보 회수(경로 깊이 30)**: 10위 밖 59건 중 47건(80%)이 "경로 밖"이고 7건이 절단이다. 그중 15건(C1 11 + D 4)은 깊이 제한만 없으면 가산 뒤 30위 안이다. 리랭킹 단계 실패(E1+E2)는 5건뿐이다
2. Context 경로는 설계대로 작동하지만 **닿는 질의가 적다**: 단서 37건 → 정답에 사실 있음 11 → 필터 통과 3. 병목은 ① 정답 곡의 사실 부재(26건), ② 작품명 일치 필터(4건), ③ 분석이 배경지식 단서를 안 뽑음(6건)의 순이다

## 5. 다음 개선 실험 1개 (이 결과로 고르면)

**속성 조건 보조 후보 조회** — 분석이 뽑은 시기·성별·장르·편성 조건으로 Qdrant payload 필터 검색을 한 번 더 해서(경로 깊이 30은 그대로), 그 목록을 다섯 번째 RRF 목록(가중 작게)으로 넣는 A/B.
