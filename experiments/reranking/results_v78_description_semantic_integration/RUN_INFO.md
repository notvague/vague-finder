## 1. 고정하는 변경 — B = A + 소개 의미 보조 경로

1. **검색**: 질의 벡터 = KoE5 `"query: " + analysis.search_text`(정규화). 청크 점수 = 색인 벡터와의 내적. 묶음 점수 = 청크 최댓값(근거 청크 = 최댓값 청크 중 번호가 작은 것). (점수 내림, 묶음 id 오름) 위 **10묶음**.

## 2. 질의 벡터 재사용(사전 고정)

- 재사용 조건: 기존 텍스트 본 경로(`path.text`)의 dense 입력 문장이 `analysis.search_text`와 **글자까지 같을 때**만. 모델은 같은 `SearchService.text_embedder` 객체(같은 KoE5 · 같은 `normalize=True` · 같은 `"query: "` 접두)이므로 입력이 같으면 같은 계산이다. 가사 의미·음차 표기가 덧붙는 질의는 입력이 달라 재사용하지 않고 한 번 더 임베딩한다.
- 방식: 요청마다 만드는 전달 칸(요청 객체에 묶인 future) 하나. 본 경로가 임베딩한 직후 (입력 문장, 벡터)를 넘기고, 보조 경로는 입력 문장이 같을 때만 그 벡터를 쓴다. **전역 캐시 · 요청 사이 공유 없음.** 본 경로가 벡터를 넘기지 못하고 끝나면(예외) 보조 경로가 직접 임베딩한다(기록 `own_after_text_path_failure`).
- 다른 경로(균형 의미 · 속성 보조 · 작품명 보조 등)가 같은 문장을 다시 임베딩하는 기존 동작은 바꾸지 않는다(A와 같게).
- 확인: 하네스가 `KoE5Embedder.embed_passages` 호출을 질의별로 센다(입력 지문 · 시간). **B − A 호출 수 = 직접 임베딩한 질의 수**여야 하고, 재사용 질의는 B − A = 0이어야 한다. v77의 "140/176"은 입력 비교일 뿐이며 이번에 호출 수로 다시 센다.

- 사전 규칙대로 **보류**한다. 실제 Vertex 리랭킹 평가 계획을 쓰지 않고, 가중·깊이·대표곡·발동 조건을 dev에서 바꿔 다시 재지 않는다(§5-3 · §6).
- 보류 이유는 하나지만 무겁다. 기존 성공 질의의 후보 탈락이 1건 있고, 같은 구조의 끝자리 교체(보조 10곡 중 여러 곡이 경계를 넘음)가 성공 질의 23건의 정답 순위를 내렸다. 전송 프롬프트는 132질의(성공 85)에서 바뀌었다.
- 별도 위험(§5-4): 프롬프트 변화 132(성공 85) · 성공 정답 순위 하락 23 · 허브 진입 92건(10질의 이상 묶음).
- 해석(외부 리뷰 반영):
  - 후보 회수는 순증 +4다. Hit@10 변화는 측정하지 않았다(가짜 리랭커).
  - n019는 후보 30 밖으로 빠져 리랭커가 복구할 수 없는 손실이다. 새로 든 6건이 10위 안에 드는지는 모른다. 따라서 최종 품질의 개선·악화를 단정하지 않는다.
  - 기존 성공 85건의 프롬프트도 바뀌었으므로 효과를 "정답 6개 추가"로만 읽지 않는다.
  - 소개에서 정답을 찾는 것과 기존 후보에 안전하게 합치는 것은 별개의 문제다. 고정 가산이 경로 간 경쟁을 다루지 못한다는 점은 후속 가설로 남긴다(`DECISION.md` §3 · H-e).
