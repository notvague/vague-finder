# v0.21 — CE가 **채점할 후보 수**를 줄인다 (30 → 20) · 2026-09-25

**결과: 요청 시간 중앙값 5.09초 → 4.21초(−17.4%). 현재 82질의(dev 57 · test 25)에서
평가 지표가 전부 같다.**

범위를 좁혀 적는다 — **일반적인 품질 무손실을 보장하는 것이 아니다.** 21위 이하
후보가 top-10으로 올라오던 경우가 test에 둘 있었고, 그 승격은 이제 막힌다
(아래 "남은 2건의 원인").

처음 측정에서는 test q201이 1위 → 2위로 내려갔었다. 원인은 잘려 나간 후보가
아니라 **검색 점수 정규화 범위가 함께 좁아진 것**이었고, 그것을 고치자 손실이 사라졌다
(아래 "무엇이 문제였나").

## 먼저 정한 것 — 재기 전에 결정한 설계

| 결정 | 왜 |
|---|---|
| **검색 후보 풀은 30 그대로** (`candidate_k` 안 건드림) | 줄이면 검색 후보 구성 자체가 바뀌어 CE 효과와 섞인다 |
| CE 채점 대상만 30 → 20 (`RERANKER_SCORE_TOP_N=20`) | 비용이 줄어드는 곳은 여기다 |
| **검색 점수는 받은 후보 30개 전체로 정규화** | 점수는 이미 손에 있고 CE 호출도 더 들지 않는다. 좁히면 합성의 저울이 달라진다 |
| 채점 안 한 후보는 **검색 순서 그대로 맨 뒤** | 점수가 없으니 순서를 정할 근거도 없다 |
| 채점 안 한 곡은 `judged_ids`·`mixes`에서 **제외** | 모델이 본 적 없는 곡에 "리랭킹됐다"를 붙이면 설명이 거짓이 된다 |

`low_conf_top_n`과 다르다 — 그것은 **전부 채점한 뒤** 상위 N개만 재정렬하므로 시간이 줄지 않는다.

**가사 보호와의 관계**: 보호는 라우터가 **배치**를 정하고 채점은 리랭커가 한다. 캡은
리랭커가 받은 목록에 걸리므로 보호 그룹은 따로 캡을 받는다. 다만 dev 57건에서는
질의당 CE 호출이 **1회뿐**이라(보호 다중 호출 경로가 거의 안 탄다) 이 실험은 그 경로를
말하지 않는다.

## 무엇이 문제였나 — 검색 정규화 범위까지 좁았다

첫 구현은 `_minmax`를 **채점한 20곡**으로 돌렸다. CE 점수는 20개밖에 없으니 어쩔 수
없지만, **검색 점수는 30개 모두 손에 있는데도** 20개 기준으로 다시 폈다. 그러면
20번째 곡이 0으로 눌리는 등 합성의 저울이 통째로 달라진다.

q201에서 정답−오답 합성 점수 차이(양수면 정답이 앞):

| 조건 | 정답 − 오답 |
|---|---|
| 30곡 채점 | +0.000849 |
| 20곡 채점 (정규화도 20곡) | **−0.010278** |
| 20곡 채점 + **검색 정규화는 30곡** | +0.000848 |

**주범은 spread의 미세한 변화가 아니라 이 범위 축소였다.** 고친 뒤 정규화는 받은
후보 전체로 하고, 앞 20곡에 해당하는 값만 합성에 쓴다. CE 호출은 늘지 않는다.

## 품질 — 정답 순위 변화 0건

| | dev 57건 | test 25건 |
|---|---|---|
| Hit@1 / Hit@5 / Hit@10 | 0.4035 / 0.6842 / 0.7895 (전부 동일) | 0.5600 / 0.5600 / 0.6800 (전부 동일) |
| Recall@10 / MRR@10 / nDCG@10 | 0.7749 / 0.5357 / 0.5938 (전부 동일) | 0.6381 / 0.5774 / 0.5815 (전부 동일) |
| **Top-10 기준 정답 순위가 달라진 질의** | **0건** | **0건** |
| 반환 Top-10 목록이 다른 질의 | **0건** | 2건 (q214 · q305) |

test 25건은 이미 여러 번 쓴 분할이므로 **회귀 확인이지 새 홀드아웃 검증이 아니다.**

### 고치기 전후

| | Top-10 정답 순위 다름 | 반환 목록 다름 |
|---|---|---|
| 20곡 채점 (정규화도 20곡) | dev 0 · **test 1**(q201) | dev **4** · test **4** |
| 20곡 채점 + 검색 정규화 30곡 | dev 0 · **test 0** | dev **0** · test **2** |

**"정답 순위 변화 0건"은 Top-10 기준이다.** 평가 CSV는 top-10 밖 순위를 빈칸으로
적으므로 그 바깥의 이동은 드러나지 않는다. 실제로 q214의 정답은 전체 순서에서
**20위 → 17위**로 움직였다(둘 다 top-10 밖이라 지표는 그대로다).

### 남은 2건의 원인 — 정규화가 아니라 **승격 차단**이다

대조군을 보면 두 질의 모두 **21위 이하 후보가 top-10에 올라와 있었다.**

| | 대조군에서 |
|---|---|
| q214 | 검색 **25위** 곡이 최종 **1위** |
| q305 | 검색 **30위** 곡이 최종 **7위** |

20곡 제한에서는 이 곡들을 **채점하지 않으므로** top-10에 올라올 수 없다. q305는
기록된 `spread`가 두 조건에서 **완전히 같다**(0.3758967463) — 그쪽은 정규화가 아니라
오직 승격 차단이 원인이다. q214는 25위 곡이 빠지면서 CE 점수 폭까지 달라졌다
(spread 0.0967 → 0.0140).

두 질의 모두 **지표는 움직이지 않는다** — q214는 어느 쪽도 정답을 top-10에 못 넣고,
q305는 정답이 1위 그대로다.

### "21위 이하 승격이 없다"는 **dev 한정이다**

dev 대조군에서 최종 top-10에 든 570곡 중 21위 이하에서 올라온 곡은 0건이었다
(최대 20위, p95 10위). **test에서는 위와 같이 두 번 일어난다.** 그러므로
"승격이 없으니 안전하다"는 dev에만 해당하는 말이고, 일반적인 품질 무손실 보장이 아니다.

dev에서 관측된 최대 승격이 정확히 20위였으므로 **15로 낮추면 그 사례를 자른다.**
더 낮추려면 다시 재야 한다.

## 채택 — 이 측정이 새 운영 기준선이다

`RERANKER_SCORE_TOP_N=20`을 채택했다(2026-09-25). `.env`와 `.env.example` 둘 다에 있다.

| | |
|---|---|
| **새 운영 기준선** | 이 폴더의 `scored20_fullnorm` (dev 57 · test 25) |
| 보존 | `results_v19_v06` — 전체 채점 기준선. 되돌릴 때 비교 대상 |
| 코드 기본값 | **0(전체 채점) 그대로** — 환경 변수만 지우면 복귀한다 |

**같은 조건으로 v06을 다시 찍지 않는다.** 그 숫자가 곧 `scored20_fullnorm`이다.

이 값은 **리랭커를 만들 때 한 번 읽는다.** 켜든 되돌리든 서버를 다시 띄워야 한다.
떠 있는 서버에 적용됐는지는 응답의 `score_mix.strategy`로 본다 —
`"후보 전체 재정렬 · 앞 20개만 채점"`이면 먹은 것이다.

산출물: `scored30`(대조) · `scored20`(정규화 범위가 좁았던 첫 판, 비교용으로 남김) ·
`scored20_fullnorm`(고친 판) · `latency_*`.
