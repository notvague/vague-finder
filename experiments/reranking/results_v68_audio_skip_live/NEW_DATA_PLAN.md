# 새 평가 자료 수집·분할 계획 — 소리 경로·작품명 해석 채택 판단용(4차 세트 초안)

작성 2026-10-17(v68). **아직 수집하지 않았다.** 이 문서와 `new_data/`(양식·점검 도구)는 준비물이다.

## 0. 왜 새 자료가 필요한가 · 지금 자료의 한계

- dev 176(v06 57 · v09 59 · v10 60)은 v23 이후 거의 모든 정책·가중 선택에 쓰였다. v09 test 38 · v10 test 42도 이미 열렸다(v34·v55). **어느 것도 독립 홀드아웃이 아니다.** v67 진단·v68 A/B도 이 dev를 썼으므로 그 결과는 "새 자료에서 다시 잴 가치가 있는가"의 근거일 뿐이다.
- **실제 서비스 사용자 질의는 없다.** 서비스는 공개되지 않았고 피드백 수집은 기본 꺼짐이다(`FEEDBACK_COLLECTION_ENABLED=0`). 그래서 이번 계획의 "실제 기억" 자료는 **팀원·지인이 자기 기억으로 쓴 질의**다. 이것은 실제 사용자 분포의 대리이지 실제 사용자 자료가 아니며, 보고서에 그 한계를 그대로 적는다. 서비스 공개 뒤 동의받은 실제 질의가 생기면 같은 절차로 별도 세트를 만든다.
- 기존 v10은 팀원이 작성 규칙(`docs/eval/query_writing_guide.md`)대로 썼다. 이번에는 그 규칙을 이어받고 아래를 더한다: 곡 단위 분할을 **수집 직후·결과 전**에 확정, 전체 분포 세트와 집중 진단 세트 분리, 누출 자동 검사, 봉인 세트 보관자 분리.

## 1. 세트 구성 — 두 갈래를 섞지 않는다

| 갈래 | `track` | 목적 | 작성 방법 | 지표 사용 |
|---|---|---|---|---|
| **전체 분포** | `general` | 서비스 품질(채택 판단의 주 지표) | 유형 할당량 없이 **실제로 떠올린 곡을 떠올린 방식대로**. 소리·표지·작품명·가사·시기·모호·틀린 기억·짧은 질의가 자연 비율로 섞이게 둔다 | 주 지표(Hit@1/5/10·MRR@10) |
| 소리 집중 진단 | `diag_sound` | 소리 경로 on/off의 손실 위치(이름 붙은 소리·악기·음색) | 소리 단서 위주로 쓴다. 이름 붙은 소리 사건(사이렌·휘파람·박수 등)을 일부러 포함 | 진단 표만. 전체 지표에 합치지 않는다 |
| 작품명 집중 진단 | `diag_work` | 간접 지칭 해석(드라마·예능·경연·영화를 줄거리로만 말함) | 작품명을 쓰지 않고 줄거리·인물·상황으로만. 작품이 여럿 떠오를 수 있는 모호한 서술도 포함 | 진단 표만 |

- 전체 분포 세트가 "소리 질의가 적어서 소리 경로를 꺼도 손해가 작다"고 말하면 그것이 실제 분포에서의 답이다. 집중 진단 세트는 **어디서 잃는지**를 보는 용도이고, 집중 세트 결과로 전체 품질을 말하지 않는다.
- 각 갈래 안에 반드시 포함(자연 비율로 부족하면 작성자에게 "이런 기억도 있으면 쓰라"고만 안내, 유형 할당은 하지 않음): 모호한 단서(곡 여러 개에 맞을 수 있음) · 잘못된 기억(성별·시기·장르·솔로/그룹·악기 중 하나) · 단서끼리 충돌 · 짧은 질의(15자 이하) · 정답을 끝내 못 찾은 질의(`unresolved`, 따로 셈).

## 2. 작성 규칙(기존 가이드 + 추가)

1. **기억으로 먼저 쓰고 정답은 나중에 확인한다**(`written_before_lookup=yes`). 정답을 먼저 정하고 쓴 질의는 `no`로 표시하고 주 지표에서 따로 본다.
2. **제출 전에 검색 시스템에 넣어 보지 않는다.** 화면·API·평가 결과를 보지 않는다. 지금 무엇이 잘 되고 안 되는지 PM·에이전트에게 묻지 않는다.
3. 곡의 파이프라인 산출물(태그·요약·sound_tags·가사 요약·Context 사실)을 보지 않는다. 정답 확인은 제목·가수·발매일·표지(메타)만으로 한다.
4. 제목·가수 이름을 쓰지 않는다(형태 기억은 된다). `diag_work`는 작품명도 쓰지 않는다.
5. 기존 질의의 바꿔쓰기 금지: 기존 세트(v04~v10, test 포함)를 보고 쓰지 않는다. 같은 곡을 떠올렸으면 버리고 다른 곡을 쓴다(자동 검사가 걸러 내도 처음부터 피한다).
6. 합성(LLM이 쓴 질의·에이전트 초안)은 `memory_source=synthetic`으로만 들어오고 **분할에서 제외**된다 — 계약 시험·스트레스 시험용이며 독립 품질 증거로 쓰지 않는다.
7. 사람마다 다른 기억: 지인에게 받은 질의는 `helped_recall` 또는 `own_memory`(그 사람 기억)로 적고, 받은 그대로 옮긴다(다듬지 않는다).

양식: `new_data/collection_template.csv`(열: `tmp_id · writer_id · written_at · memory_source · written_before_lookup · query · track · clue_types · tier · wrong_clue · ambiguity · writer_confidence · positive_id · positive_title · positive_artist · corpus_status · other_version_ids · answer_check_by · answer_check_result · notes`).

## 3. 정답 확인 — 질의를 다 쓴 뒤

- 작성자가 기억하는 곡을 메타(제목·가수)로 코퍼스(`data/all_songs.jsonl`, 현재 5,143곡)에서 찾아 `positive_id`를 적는다. 끝내 못 찾으면 비워 둔다(`unresolved`).
- **두 번째 사람**이 같은 메타 검색으로 정답을 독립 확인한다(`answer_check_by` · `answer_check_result` = `same | different | unsure`). 다르면 둘이 협의하고, 합의가 안 되면 `ambiguity`에 적고 주 지표에서 따로 센다.
- 코퍼스 밖(`out_of_corpus`)은 평가에서 빼고 건수만 보고한다(크롤링으로 곡을 늘려 맞추지 않는다 — 수집 자료를 보고 코퍼스를 바꾸면 그것도 누출이다). 다른 판(리메이크·라이브)이 있으면 원곡을 정답으로, 다른 판 ID는 `other_version_ids`에.

## 5. 분할 — 결과를 보기 전에, 사람이 고르지 않게

- 분할 단위는 **곡**(정답 ID). salt를 붙인 sha256으로 `policy_dev` / `sealed`를 정한다. **salt는 튜닝하지 않는 보관자**(예: 이번 개발을 하지 않는 팀원 1인)가 만들어 혼자 보관한다. 저장소·워크트리·에이전트 세션에 두지 않는다.
- 비율: `sealed` 60% · `policy_dev` 40%(갈래마다 따로). 작성자는 분할을 고르지 않는다.
- 규모(목표 · 근거): Hit@10이 약 0.67일 때 질의 n건의 95% 신뢰구간 반폭은 n=100 ±9.2%p · 150 ±7.5%p · 300 ±5.3%p. 두 구성 비교는 질의별 짝 비교(McNemar)라 결론이 갈리는 질의 수가 중요하다 — v68처럼 구성 차이가 질의의 몇 %에서만 나는 변경은 **봉인 전체 분포 세트 150건 이상**에서도 작은 차이를 확정하기 어렵다. 그래서 목표는 전체 분포 세트 **250건 이상(sealed 150 · dev 100)**, 진단 세트 각 40~60건이고, 결과는 신뢰구간·짝 비교 수와 함께 보고한다. 이 규모를 못 채우면 "큰 차이만 판별 가능"이라고 적는다.

## 6. 평가 절차 — 같은 신규 자료에서 기존 구성과 개선 구성을 함께

1. 구성 동결: 비교할 구성(예: A 현행 · B 소리 생략 · 이후 작품명 해석 구성)을 커밋 SHA·환경·색인·가사·분석기 지문으로 **봉인 평가 전에** 고정한다. 정책 개발은 `policy_dev`에서만 한다.
2. `policy_dev` 측정: 분석 캐시 생성(Vertex, 예산 별도 승인) → 구성별 2회 이상(동시 대조군) → 실패 포함 분모.
3. **봉인 평가는 구성 목록을 정한 뒤 한 번만**: 보관자가 실행하거나, 실행자가 질의 원문을 보지 않는 하네스(질의는 보관자 폴더에서 읽고, 출력은 집계·짝 비교 수·신뢰구간만)로 돌린다. 질의별 실패 분석은 하지 않는다 — 하는 순간 그 세트는 개발용으로 강등하고 새 봉인 세트를 만든다.
4. 보고: 전체 분포 세트의 주 지표(신뢰구간) · 짝 비교(얻음/잃음) · 진단 세트 표(따로) · 코퍼스 밖·미확인·합성 제외 건수 · "실제 사용자 자료가 아니라 팀원·지인 기억 자료"라는 한계.

### 6-1. 봉인 내용이 튜닝 세션에 새지 않게

- 봉인 파일(`sealed.csv`·`checked.csv`·salt)은 보관자 개인 드라이브에만 둔다. 저장소에 커밋하지 않고 워크트리·`/private/tmp`·에이전트 스크래치에 복사하지 않는다.
- 튜닝 세션(사람·에이전트)은 `policy_dev.csv`와 `report.json`(건수만)만 받는다. 에이전트 지시문에 봉인 경로를 쓰지 않는다.
- 봉인 평가 하네스는 질의 원문·질의별 순위를 출력하지 않는다. 출력 파일은 집계만. 실행 로그·explain·detail은 보관자 폴더에만.
- 봉인 세트를 연 날짜·구성·결과를 RUN_INFO에 기록하고, 같은 세트로 다시 고르지 않는다(재사용 금지 표시).

## 7. 이 계획이 하지 않는 것

- 새 자료를 모델로 생성하지 않는다(합성은 제외 표시). 기존 dev의 라벨·분모를 고쳐 맞추지 않는다.
- 수집 자료를 보고 코퍼스·색인·분석 프롬프트를 바꾸지 않는다(바꾸면 그 변경 전에 봉인 평가를 끝내거나 세트를 새로 만든다).
