## 3. 정렬·식별 계약(실행 전 확정 — dev 결과·정답 여부로 고르지 않는다)

1. **순서**: 점수 내림차순 → `song_id` 오름차순. Context 사실은 → `song_id` → `record_id`, Context 프로필은 → `song_id` → `profile_id`.
2. **song_id 비교 규칙** `song_id_sort_key`: 앞뒤 공백을 뗀 문자열 `s`에 대해
   - `s`가 ASCII 숫자만이면 `(0, int(s), s)` — 숫자 값 순, 같은 값(앞자리 0 차이)이면 문자열 순
   - 그 밖(빈 문자열 제외)은 `(1, 0, s)` — 숫자형 뒤, 유니코드 코드포인트 순(정규화 없음)
   - 근거: 곡 id는 멜론 숫자 id이고 point id도 같은 숫자다. 길이가 섞여 있어 문자열 순서는 숫자 의미와 어긋난다. 이 규칙은 자료의 형식만 보고 정했다.
   - `record_id`·`profile_id`는 문자열 그대로 코드포인트 순.
3. **식별자**: 정렬 키는 payload의 원래 `song_id`(Context는 `record_id`/`profile_id`)다. point id·UUID·삽입 순서·백엔드 반환 순서를 쓰지 않는다.
   - 곡 컬렉션: payload `song_id`가 없거나 빈 점은 **후보가 아니다**(경고 로그, 결과에서 뺀다 — point id로 대신하지 않는다). 같은 song_id의 점이 둘이면 앞자리만 남긴다(적재기는 `point_id(song_id)`로 점을 만들어 이런 점이 없다).
   - **실행 전 변경(결과를 보기 전, 2026-10-17 11:4x)**: 처음에는 "`point_id(song_id) != point.id`인 점도 후보 아님"을 넣었다. 기존 시험 자료(`tests/test_qdrant_backend.py`)가 point id 1 ↔ song_id "a"처럼 둘을 따로 두는데, 정렬 계약에 point id 일치는 필요 없어서 뺐다. 실자료는 5,143/5,143 일치(§2)라 결과에는 영향이 없다.
   - Context: 기존 계약대로 세대·schema·종류가 맞지 않는 점은 예외(`RuntimeError`) — 바꾸지 않는다.
   - payload를 읽지 않던 하이브리드 전수 조회는 합산 뒤 **경계까지의 점**(top_k + 경계 동점)만 payload를 읽어 키를 얻는다.
4. **동점의 정의**: 백엔드가 돌려준 점수(float)가 **정확히 같을 때만** 동점이다. epsilon·반올림을 넣지 않는다. 백엔드 사이 점수의 작은 차이(같은 벡터인데 마지막 비트가 다름 등)는 동점 처리로 덮지 않고 따로 집계·보고한다.
5. **경계 완전성**: top_k를 돌려줄 때 k번째 점수와 같은 점수를 가진 점을 **모두** 확보한 뒤 위 순서로 정렬해 k개를 자른다.
   - 비하이브리드(이미지·오디오·텍스트 dense만)와 Context 두 조회: 첫 조회 `limit = k+1`. (k+1)번째 점수 < k번째 점수이거나 반환이 limit보다 적으면 끝(추가 비용 = 1점). 아니면 limit을 두 배로 늘려 다시 조회하고, **마지막 반환 점수 < k번째 점수**이거나 반환이 limit보다 적어질 때까지 반복한다. 정확 검색(`exact=True`)의 상위 L개는 점수 순으로 정확하므로 종료 조건이 성립하면 k번째 점수 이상인 점은 빠짐없이 들어 있다. 상한 상수를 두지 않는다(대상 수가 끝이다).
   - 하이브리드: v62부터 이미 전수 조회라 집합은 완전하다. 합산 정렬에만 위 순서를 쓴다.
   - count 캐시를 두지 않는다. 새 고정 상한을 두지 않는다.
6. 이 계약 아래의 집계(`_rrf_fuse`·Context 곡별 집계·RRF·단서 결합·근거 목록)는 입력 순서에 대해 결정적이므로 바꾸지 않는다. 실제로 필요하다는 증거(수정 후에도 남는 차이)가 나오면 그때 고친다.
7. **불변 복사본 기준**이다. count·조회·payload 읽기 사이의 동시 적재는 이번에도 보장하지 않는다(v62 전제 유지).

## 7. 판단

- **오프라인 결정성 검증은 끝났다**: 같은 자료·조건에서 로컬 파일과 서버가 동일한 후보 집합을 만들고(176/176), 순서·리랭커 입력·프롬프트는 174~175/176에서 같다. 반복·서버 재시작·재적재에 흔들리지 않는다. 경계 동점은 독립 기준과 대조해 빠짐없이 확보됐다.
- **남은 차이는 동점 처리 밖이다**: 2질의의 근소 차이는 백엔드가 계산한 점수 자체가 다르기 때문이다(정밀도). 이 PR 범위의 계약(정확한 동점만 동점)으로는 없앨 수 없고, 없애려면 별도 설계(고정 정밀도 재채점)가 필요하다.
- **실제 모델 품질은 재지 않았다.** 동점 수정이 리랭킹 뒤 Hit/MRR에 주는 영향, 수정 후 서버 조건의 기준선은 없다(계획·예산안: `LIVE_REMEASURE_PLAN.md`). 리랭킹 전 숫자(122·41·102)는 수정 전후 같지만 품질 근거가 아니다.
- 이 수정만으로 **D 활성화나 서버 배포 준비가 끝난 것이 아니다**: D는 여전히 증거 부족(v64 판단서), 서버 적재는 검색 중단 절차 전제(v62·v64), 동시 적재는 보장하지 않는다.
