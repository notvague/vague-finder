# 독립 평가 자료 수집 요청안 — 지금 시작(v76, 2026-10-20)

**수집 0건 · 이 세션은 질의를 쓰거나 정답을 확인하지 않았다.** 사람이 할 일을 요청하는 문서다. 절차·양식·점검 도구는 기존 계획을 그대로 쓴다: v68 `results_v68_audio_skip_live/NEW_DATA_PLAN.md`(기본 절차 · `new_data/` 도구) · v69 `results_v69_audio_skip_repeat/NEW_DATA_PLAN.md`(전체 분포와 진단 세트 분리) · v70 `results_v70_work_name_resolution/NEW_DATA_PLAN.md`(작품 라벨 열). 이 요청안은 그 계획을 바꾸지 않고, **개선 작업과 나란히 지금 시작**하기 위한 담당·순서·첫 묶음만 정한다.

## 1. 왜 지금인가

- dev 176은 v23 이후 거의 모든 정책 선택에 쓰였고 v09·v10 test도 열렸다. 독립 홀드아웃이 없다.
- 개선 후보(v76 소개 보조 등)가 완성된 뒤에 모으면, 그 후보가 잘하는 질의를 무의식적으로 모을 위험이 있다. 그래서 **후보를 보기 전에** 모으고 나눠 봉인한다.
- 순서: **지금 수집 시작 → 개선 후보와 채택 기준(지표 우선순위 · 판정 규칙)을 고정 → 그 뒤 봉인 세트를 한 번 연다.** 채택 판단은 봉인 세트에서만 한다.

## 2. 요청 — 사람이 정해 줄 것(PM)

| 항목 | 요청 | 비고 |
|---|---|---|
| 작성자 | 팀원·지인 여러 명(한 사람 몫이 전체의 20%를 넘지 않게) | 이번 개선 작업을 직접 보지 않은 사람이 좋다 |
| 정답 확인자 | 작성자와 다른 사람 1명 이상 | v68 §3 |
| salt 보관자 | 이번 개발(튜닝)을 하지 않는 사람 1명 | salt·봉인 파일을 혼자 보관. 저장소·워크트리·에이전트 세션에 두지 않는다 |
| 목표 규모 | `general` 250건 이상(sealed 150 · policy_dev 100) · `diag_work` · `diag_sound` 각 40~60건 | v68 §5. 못 채우면 "큰 차이만 판별 가능"으로 적는다 |
| 일정 | 첫 묶음(예: `general` 50건)부터 수집 → 점검 → 분할을 묶음마다 바로 한다 | 다 모일 때까지 기다리지 않는다. 분할은 결과를 보기 전에 확정 |

## 3. 작성자에게 줄 안내(그대로 전달)

1. 실제로 기억나는 곡을 떠올린 **그대로** 쓴다. 쓰기 전에 검색 시스템·검색 결과·곡의 태그·요약을 보지 않는다.
2. 제목·가수 이름은 쓰지 않는다. `diag_work`는 작품명(드라마·예능·경연·영화 이름)도 쓰지 않는다.
3. 질의를 **다 쓴 뒤**에 정답 곡을 제목·가수·발매일·표지로만 확인한다. 못 찾으면 비워 둔다.
4. 지금 시스템이 무엇을 잘하고 못하는지 PM·에이전트에게 묻지 않는다. 기존 평가 질의를 보고 바꿔 쓰지 않는다.
5. `general`에는 유형 할당이 없다 — 소리·작품명·맥락 같은 특정 유형을 쓰라고 권하지 않는다(분포가 바뀐다).

## 4. 받은 뒤 처리(사람 · 도구)

1. 양식 `new_data/collection_template.csv`(+ v70 작품 라벨 열) 확인 → 두 번째 사람의 정답 확인.
2. `new_data/new_data_check.py`(형식·코퍼스·누출·중복·곡 단위 분할) · `new_data/work_label_check.py`.
3. salt 보관자가 곡 단위 분할(sealed 60% · policy_dev 40%, 갈래마다) → 개발 쪽에는 `policy_dev.csv`와 건수 보고(`report.json`)만 넘긴다.
4. 합성 질의(모델이 쓴 질의·에이전트 초안)는 분할에서 빠진다(`memory_source=synthetic`). 실제 기억 자료를 대신하지 않는다.

## 5. v76과의 관계 — 진단 갈래를 새로 만들지 않는다

- v76이 겨냥한 실패(곡이 놓인 맥락 — 경연·원곡·참여 형태 — 를 일반어로 말함)는 기존 `diag_work`(작품명을 쓰지 않고 줄거리·상황만)와 `general`에서 자연히 나온다. **v76용 질의 유형을 따로 요청하지 않는다** — 요청하면 v76에 유리한 질의가 모인다.
- v76 채택 판단은 `general`(policy_dev로 개발, sealed로 1회 판정)에서만 한다. `diag_work` 결과는 손실 위치 확인용이다.
- 이 개발 세션(에이전트)은 봉인 자료의 원문·정답을 읽지 않는다. 개발에 쓴 자료(dev 176 · policy_dev)를 나중에 독립 평가 자료라고 부르지 않는다.
